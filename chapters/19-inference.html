Inference and Serving

Training happens once; inference happens billions of times a day. By 2026, inference is the largest and fastest-growing share of AI compute spend, and cost per token is the number that decides which AI products are viable. This is the chapter most directly tied to money.

The metrics

Metric Meaning Who cares
TTFT (time to first token) Wait before output starts; dominated by prefill and queueing Chat UX, voice agents
TPOT / ITL (time per output token, inter-token latency) Speed of streaming; dominated by decode Readability, agent speed
Throughput Total tokens/sec across all users on the hardware Cost
Goodput Requests/sec that meet latency SLOs The real business metric
Cost per million tokens GPU $/hour ÷ tokens/hour Finance
p50 / p95 / p99 latency Tail latency SLAs

End-to-end latency ≈ TTFT + TPOT × (output tokens − 1).

Prefill and decode

The decode-step speed limit for a single sequence is roughly:

time per token ≥ (bytes of weights read + bytes of KV cache read) ÷ HBM bandwidth Llama-3-8B in BF16 on an H100: 16 GB ÷ 3.35 TB/s ≈ 4.8 ms → ≤ ~210 tokens/s for one user

Serving 64 users in one batch reads the weights once per step for all 64, so throughput rises nearly 64× until compute or KV-cache memory runs out. Every serving optimisation either increases the batch you can fit, reduces bytes per token, or reduces the number of sequential steps.

The KV cache

To avoid recomputing attention over the whole history at every step, the server stores each past token's keys and values.

KV bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes per element
def kv_per_token(layers, kv_heads, head_dim, bytes_=2):
    return 2 * layers * kv_heads * head_dim * bytes_

models = {
    "Llama-2-7B (MHA, 32 kv heads)": (32, 32, 128),
    "Llama-3-8B (GQA, 8 kv heads)":  (32, 8, 128),
    "Llama-3-70B (GQA, 8 kv heads)": (80, 8, 128),
}
for name, cfg in models.items():
    b = kv_per_token(*cfg)
    print(f"{name}: {b/1024:.0f} KB/token, {b*8192/1e9:.2f} GB for one 8K-token sequence")
# Llama-2-7B: 512 KB/token -> 4.29 GB per 8K sequence
# Llama-3-8B: 128 KB/token -> 1.07 GB
# Llama-3-70B: 320 KB/token -> 2.68 GB

On an 80 GB GPU running Llama-3-8B (16 GB weights), ~60 GB remain for cache: about 56 concurrent 8K-token conversations. KV cache capacity sets your maximum batch size, which sets your cost. This is why GQA, MLA, hybrid attention, KV quantization and KV offloading matter so much.

Continuous batching

Static batching waits for all sequences in a batch to finish, so short answers idle while long ones complete. Continuous (in-flight) batching (Orca, 2022) makes scheduling decisions every iteration: finished sequences leave, new ones join immediately.

Chunked prefill splits long prompts into chunks mixed into decode batches, so one huge prompt doesn't freeze everyone else's streaming.

PagedAttention

Before vLLM, servers reserved contiguous KV memory for each request's maximum length, wasting 60–80% of cache memory to fragmentation. PagedAttention (vLLM, 2023) stores the cache in fixed-size blocks (e.g., 16 tokens) addressed through a per-sequence block table, like virtual memory pages in an operating system. Waste drops below 4%, batch sizes rise 2–4×, and blocks can be shared between sequences with a common prefix.

Prefix caching

Many requests share a prefix: the same system prompt, the same RAG documents, the previous turns of a conversation, or an agent's growing context. Prefix caching keeps those KV blocks and reuses them, skipping prefill for the shared part. SGLang's RadixAttention stores prefixes in a radix tree. Commercial APIs expose this as prompt caching with large discounts on cached input tokens.

Business impact: for agents and chat, cache hit rates of 50–90% are common, cutting TTFT and cost dramatically. Designing prompts so the stable parts come first ("cache-friendly prompts") is a real optimisation.

Quantization

Fewer bytes per weight = less to read per decode step and more room for KV cache.

Method What is quantized Notes
FP8 (W8A8) Weights and activations Near-lossless on Hopper/Blackwell; default for large-model serving
INT8 (SmoothQuant, LLM.int8) Weights and activations Moves activation outliers into weights
GPTQ, AWQ Weights to 4-bit (W4A16) Great for small-batch, memory-bound serving
NVFP4 / MXFP4 Weights and activations to 4-bit float with block scales Blackwell/Rubin native; gpt-oss shipped in MXFP4
GGUF (llama.cpp) 2–8-bit weights, many schemes Laptops and CPUs
KV cache FP8 / INT4 The cache Doubles or quadruples context capacity

from llmcompressor import oneshot
from llmcompressor.modifiers.awq import AWQModifier
oneshot(model="meta-llama/Llama-3.1-8B-Instruct",
        dataset="open_platypus", num_calibration_samples=256,
        recipe=[AWQModifier(targets=["Linear"], scheme="W4A16", ignore=["lm_head"])],
        output_dir="Llama-3.1-8B-Instruct-AWQ")
# vllm serve ./Llama-3.1-8B-Instruct-AWQ

Always evaluate quality after quantizing, on your tasks. Averages hide regressions on math, code and long context.

Speculative decoding

Decode is sequential and memory-bound, so the GPU has spare compute. Speculative decoding uses a cheap draft to guess several tokens ahead; the big model verifies all guesses in one forward pass and keeps the longest correct prefix. Output distribution is mathematically unchanged.

Draft options: a small model from the same family; Medusa heads; EAGLE-3 (a light draft head on the target's hidden states, one of the best-performing methods); DeepSeek's MTP heads; n-gram / prompt-lookup (great when output copies input, like code edits). Typical speedups: 2–3× at low batch sizes; gains shrink at high batch sizes where compute is no longer idle.

Parallelism for inference

  • Tensor parallelism splits each layer across GPUs in a node: lowers latency, needed when weights exceed one GPU.
  • Pipeline parallelism across nodes for very large models.
  • Expert parallelism for MoE: DeepSeek's production deployment used large-scale EP across many nodes with separate prefill and decode clusters.
  • Data parallelism (replicas) for throughput, behind a load balancer.

Disaggregated serving

Prefill is compute-bound; decode is memory-bound. On the same GPU they interfere: a big prefill stalls everyone's decode. Disaggregation (DistServe, Splitwise, Mooncake, 2024) runs them on separate GPU pools and transfers the KV cache between them over fast interconnects.

This is now mainstream at scale: NVIDIA Dynamo, llm-d (Red Hat, Google, IBM and others on Kubernetes), SGLang and vLLM all support it, and NVIDIA's Rubin CPX chip exists specifically for the prefill side. Moonshot's Mooncake built Kimi's serving around a KV-cache-centric design.

Benchmarking properly

# load_test.py: concurrent streaming requests, measuring TTFT, TPOT, throughput
import asyncio, time, statistics
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="none")
MODEL = "Qwen/Qwen2.5-7B-Instruct"

async def one(prompt):
    t0 = time.perf_counter(); first = None; n = 0
    stream = await client.chat.completions.create(model=MODEL, stream=True, max_tokens=256,
                                                  messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            first = first or time.perf_counter(); n += 1
    end = time.perf_counter()
    return first - t0, (end - first) / max(n - 1, 1), n

async def main(concurrency=64, total=512):
    sem = asyncio.Semaphore(concurrency)
    async def run(i):
        async with sem:
            return await one(f"Write a short story about server #{i}.")
    t0 = time.perf_counter()
    res = await asyncio.gather(*(run(i) for i in range(total)))
    wall = time.perf_counter() - t0
    ttft = sorted(r[0] for r in res); tpot = sorted(r[1] for r in res)
    print(f"TTFT p50 {statistics.median(ttft)*1e3:.0f} ms  p95 {ttft[int(.95*len(ttft))]*1e3:.0f} ms")
    print(f"TPOT p50 {statistics.median(tpot)*1e3:.1f} ms")
    print(f"throughput {sum(r[2] for r in res)/wall:.0f} output tok/s")

asyncio.run(main())

Also use vllm bench serve, NVIDIA GenAI-Perf / AIPerf, and the public InferenceMAX benchmark results. Always test with realistic input/output length distributions; a benchmark of 128-token prompts says nothing about a RAG workload with 8,000-token prompts.

Cost per million tokens

def cost_per_million(gpu_hourly_usd, n_gpus, tokens_per_sec):
    return gpu_hourly_usd * n_gpus / (tokens_per_sec * 3600) * 1e6

print(cost_per_million(2.50, 1, 2500))    # one H100 at $2.50/h, 2,500 tok/s -> $0.28 / M tokens
print(cost_per_million(2.50, 1, 150))     # same GPU, unbatched, 150 tok/s  -> $4.63 / M tokens

Same hardware, 16× difference in cost, purely from batching and utilisation. This is the heart of inference engineering.

Build it

Project 1 (flagship): "Our LLM bill is too high"

Business problem: a company runs an open 8B model with naive Hugging Face generate() on dedicated GPUs and pays too much per token.

  1. Baseline: Hugging Face Transformers, batch size 1. Measure TTFT, TPOT, throughput, $/M tokens.
  2. vLLM with continuous batching and PagedAttention at concurrency 1, 16, 64, 256.
  3. Add FP8 or AWQ 4-bit quantization; measure quality on a 200-question eval.
  4. Enable prefix caching with a realistic 2,000-token shared system prompt.
  5. Add speculative decoding (EAGLE-3 or n-gram) and measure at low vs. high concurrency.
  6. Deliverable: a latency-vs-throughput curve for each configuration and a one-page recommendation: "Config X serves our traffic at $Y/M tokens with p95 TTFT under 500 ms, a Z× saving."
