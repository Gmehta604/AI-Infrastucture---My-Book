Distributed Training

No frontier model fits on one GPU, and no frontier training run finishes on one. Distributed training splits the work across thousands of accelerators while keeping them busy. This chapter covers every parallelism strategy, the communication behind each, and how they combine.

Why split at all? Two reasons

  1. Memory: a 70B model needs ~1.1 TB for weights, gradients and Adam state (16 bytes/parameter, Chapter 5), plus activations. One GPU has 80–288 GB.
  2. Time: 10²⁵ FLOPs on one H100 at 40% utilisation would take about 800 years.

Collective communication: the vocabulary

All parallelism is built from a few collective operations, implemented by NCCL (NVIDIA) or RCCL (AMD).

Collective What it does Used for
All-reduce Every rank ends with the sum of all ranks' tensors Averaging gradients in data parallelism
Reduce-scatter Sum, then each rank keeps only its 1/N slice FSDP/ZeRO gradient sharding
All-gather Each rank contributes a slice; all ranks get the full tensor FSDP gathering weights before use
All-to-all Each rank sends a different chunk to every other rank Expert parallelism (MoE token routing)
Broadcast One rank sends to all Initial weights
Send / recv Point to point Pipeline parallelism

Ring all-reduce is bandwidth-optimal: each GPU sends and receives about 2·(N−1)/N × the data size, independent of the number of GPUs. An all-reduce is literally a reduce-scatter followed by an all-gather.

# Minimal distributed script: run with  torchrun --nproc_per_node=4 allreduce.py
import torch, torch.distributed as dist, os
dist.init_process_group("nccl")
rank = dist.get_rank(); torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))
x = torch.ones(4, device="cuda") * (rank + 1)
dist.all_reduce(x, op=dist.ReduceOp.SUM)
print(f"rank {rank}: {x.tolist()}")        # every rank prints [10, 10, 10, 10] with 4 GPUs
dist.destroy_process_group()

The parallelism strategies

1. Data parallelism (DP / DDP)

Every GPU holds a full model copy and processes a different slice of the batch. After the backward pass, gradients are all-reduced so all copies stay identical. PyTorch's DistributedDataParallel overlaps the all-reduce with the backward pass by bucketing gradients.

  • Simple and scales well, but every GPU must fit the whole model plus optimizer state.

2. ZeRO and FSDP: sharded data parallelism

Microsoft's ZeRO (2019) observed that in DDP every GPU stores identical copies of optimizer state, gradients and weights, which is wasteful. Shard them:

Stage Sharded Memory per GPU for 70B on 64 GPUs (approx.)
DDP Nothing ~1,120 GB (doesn't fit)
ZeRO-1 Optimizer state ~140 + 140 + 840/64 ≈ 293 GB
ZeRO-2 + gradients ~140 + (140 + 840)/64 ≈ 155 GB
ZeRO-3 / FSDP + weights ~1,120/64 ≈ 17.5 GB (+ activations)

With FSDP, before each layer runs, GPUs all-gather that layer's weights, compute, then free them. After backward, gradients are reduce-scattered so each GPU updates only its shard. Communication is 1.5× DDP's, but memory scales down with GPU count. FSDP2 (PyTorch, per-parameter sharding with DTensor) is the modern API.

import torch, torch.distributed as dist
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

dist.init_process_group("nccl")
model = GPT(cfg).cuda()                     # from Chapter 9
mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for block in model.blocks:
    fully_shard(block, mp_policy=mp)        # shard each Transformer block
fully_shard(model, mp_policy=mp)            # then the root (embeddings, head)
opt = torch.optim.AdamW(model.parameters(), lr=3e-4, fused=True)
# the training loop is unchanged; launch with: torchrun --nnodes=4 --nproc_per_node=8 train.py

3. Tensor parallelism (TP)

Split individual weight matrices across GPUs (Megatron-LM, 2019). For the MLP: split the first matrix by columns and the second by rows; each GPU computes a partial result, and one all-reduce combines them.

Attention splits naturally by heads. TP needs all-reduces in every layer, twice forward and twice backward, so it must stay inside the NVLink domain (typically TP=8 on HGX nodes; larger on NVL72).

4. Pipeline parallelism (PP)

Put different layers on different GPUs: layers 1–20 on stage 0, 21–40 on stage 1, and so on. Split the batch into micro-batches and stream them through so stages work concurrently. The idle time at the start and end is the pipeline bubble.

Bubble fraction ≈ (p − 1) / (m + p − 1) p = stages, m = micro-batches e.g., p = 8, m = 64 → ~10% idle

Schedules: GPipe, 1F1B (one-forward-one-backward), interleaved 1F1B, zero-bubble schedules, and DeepSeek's DualPipe, which overlaps computation and communication in both directions. PP only needs point-to-point sends between neighbours, so it tolerates slower inter-node links.

5. Context / sequence parallelism (CP / SP)

For long sequences, activations are huge. Sequence parallelism splits LayerNorm/dropout activations along the sequence dimension alongside TP. Context parallelism / ring attention splits the sequence across GPUs for attention itself: each GPU holds a chunk of queries and passes K/V chunks around a ring. Essential for 128K–1M-token training.

6. Expert parallelism (EP)

For MoE models, place different experts on different GPUs. Each token is sent (all-to-all) to the GPUs holding its chosen experts and results are sent back. Communication is heavy and bursty; libraries like DeepEP (DeepSeek) optimise these kernels, and large NVLink domains help enormously.

Putting it together: 3D/4D/5D parallelism

Large runs combine them, mapped to the network hierarchy:

Llama 3 405B used TP=8, PP=16, CP up to 16 for long context, and DP for the rest, on up to 16,384 H100s. A rule of thumb: put the most communication-hungry parallelism on the fastest links. TP and EP inside NVLink, PP across nearby nodes, DP/FSDP across everything.

Fault tolerance and checkpointing

  • Checkpoint model and optimizer state regularly. For a 400B model this is several TB; write asynchronously and in parallel (PyTorch Distributed Checkpoint), or snapshot to CPU memory of peer nodes for fast recovery.
  • Elastic training (torchrun elastic, TorchFT) continues with fewer replicas when nodes fail.
  • Health checks before and during jobs: DCGM diagnostics, NCCL all-reduce tests to find slow links, straggler detection.
  • Silent data corruption: rare faulty chips compute wrong answers without crashing. Large operators run periodic checksum and redundant computation tests.

Measuring efficiency

def mfu(n_params, tokens_per_sec, n_gpus, peak_flops=989e12):
    return 6 * n_params * tokens_per_sec / (n_gpus * peak_flops)

print(f"{mfu(70e9, 1.2e6, 1024):.1%}")    # 70B at 1.2M tokens/s on 1,024 H100s ≈ 50%

(For long sequences, add attention FLOPs: about 12·L·T·d per token.)

Build it

Project: Scale a training job from 1 to 16 GPUs and explain every loss of efficiency

Business problem: a startup's fine-tuning jobs take 3 days on one node. They want to know if 4 nodes will take 18 hours or 30.

  1. Rent 2–4 nodes of 8 GPUs (RunPod, Lambda, CoreWeave, or a cloud spot cluster).
  2. Train a 1B–8B model with TorchTitan or FSDP2. Measure throughput at 1, 8, 16 and 32 GPUs.
  3. Run nccl-tests (all_reduce_perf) to measure actual bus bandwidth within and across nodes.
  4. Try TP=2 vs. pure FSDP, activation checkpointing on/off, different micro-batch sizes.
  5. Deliverable: a scaling-efficiency chart and a recommendation with cost per run.
