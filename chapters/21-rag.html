Retrieval, Vector Search and RAG

Models know what was in their training data, up to a cutoff date, and nothing about your company's documents. Retrieval-augmented generation (RAG) fetches relevant information at query time and puts it in the prompt. It is the most deployed enterprise AI pattern, and most of its failures are retrieval failures, not model failures.

The RAG pipeline

Chunking

Chunks are what you retrieve. Too small and they lack context; too large and they dilute relevance and waste tokens.

Strategy Notes
Fixed size with overlap (e.g., 500 tokens, 50 overlap) Simple baseline
Recursive / structural Split by headings, paragraphs, sentences; respect document structure
Semantic Split where embedding similarity between sentences drops
Contextual chunking Prepend an LLM-written summary of where the chunk sits in its document (Anthropic's Contextual Retrieval, 2024, cut retrieval failures by about half with reranking)
Parent–child Retrieve small chunks, feed the larger parent section to the model
Late chunking Embed the whole document with a long-context model, then pool per chunk 
def chunk_by_headings(markdown_text, max_chars=2000, overlap=200):
    sections, cur, title = [], [], "Intro"
    for line in markdown_text.splitlines():
        if line.startswith("#"):
            if cur: sections.append((title, "\n".join(cur)))
            title, cur = line.lstrip("# ").strip(), []
        else:
            cur.append(line)
    if cur: sections.append((title, "\n".join(cur)))
    chunks = []
    for title, body in sections:
        for i in range(0, max(len(body), 1), max_chars - overlap):
            chunks.append({"title": title, "text": f"{title}\n{body[i:i + max_chars]}"})
    return chunks

Parsing is often the hardest part. PDFs with tables, multi-column layouts and scanned pages need proper tools (Docling, Unstructured, LlamaParse, Azure Document Intelligence, or VLM-based parsing, Chapter 14).

Embeddings and similarity search

Each chunk becomes a vector (Chapter 8). At query time, embed the question and find nearest neighbours by cosine similarity. With millions of vectors, exact search is too slow, so we use approximate nearest neighbour (ANN) indexes.

Index How it works Trade-offs
Flat (brute force) Compare against everything Exact; fine up to ~1M vectors on GPU
HNSW Multi-layer proximity graph; greedy search from coarse to fine layers Fast and accurate; memory-hungry; the default in most vector DBs
IVF k-means clusters; search only the nearest few clusters Tunable speed/recall via nprobe
PQ / scalar / binary quantization Compress vectors (e.g., 1024 floats → 64 bytes) Huge memory savings; some recall loss; rescore top results
DiskANN Graph index on SSD Billions of vectors cheaply 
import faiss, numpy as np
d = 384
xb = np.random.rand(200_000, d).astype("float32"); faiss.normalize_L2(xb)
index = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)   # 32 links per node
index.hnsw.efConstruction = 200
index.add(xb)
index.hnsw.efSearch = 64                                         # recall/speed knob
xq = xb[:5]
scores, ids = index.search(xq, 10)
print(ids[:, 0])        # each query finds itself first

Vector databases: pgvector (Postgres extension; often all you need), Qdrant, Weaviate, Milvus, Pinecone, Elasticsearch/OpenSearch, Vespa, Turbopuffer, LanceDB, Chroma. Choose based on scale, filtering needs, hybrid search support and whether you already run Postgres.

Hybrid search and reranking

Embeddings capture meaning but miss exact terms: product codes, error messages, names. BM25 keyword search catches those. Combine both with reciprocal rank fusion (RRF), then rerank with a cross-encoder that reads the query and each candidate together, which is far more accurate than comparing separate embeddings.

from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer, CrossEncoder
import numpy as np

docs = [c["text"] for c in chunks]
bm25 = BM25Okapi([d.lower().split() for d in docs])
emb = SentenceTransformer("BAAI/bge-small-en-v1.5")
D = emb.encode(docs, normalize_embeddings=True)
reranker = CrossEncoder("BAAI/bge-reranker-base")

def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

def search(query, top_k=5):
    dense = np.argsort(-(D @ emb.encode(query, normalize_embeddings=True)))[:50]
    sparse = np.argsort(-bm25.get_scores(query.lower().split()))[:50]
    candidates = rrf([dense.tolist(), sparse.tolist()])[:30]
    scores = reranker.predict([(query, docs[i]) for i in candidates])
    return [candidates[i] for i in np.argsort(-scores)[:top_k]]

Generation with grounding

def answer(query, llm):
    hits = search(query)
    context = "\n\n".join(f"[{n+1}] {docs[i]}" for n, i in enumerate(hits))
    prompt = f"""Answer using ONLY the sources below. Cite sources like [1].
If the sources do not contain the answer, say "I don't know based on the available documents."

Sources:
{context}

Question: {query}"""
    return llm(prompt)

Advanced patterns

  • Query rewriting: turn "what about for contractors?" into a standalone question using chat history; generate multiple query variants; HyDE (embed a hypothetical answer).
  • Agentic RAG: the model decides when and what to search, iterates, and uses tools (Chapter 22). "Deep research" products are agentic RAG over the web.
  • GraphRAG: build a knowledge graph of entities and relations for questions that span many documents ("what are the main themes across all incident reports?").
  • Long context vs RAG: with 1M-token windows, you can sometimes skip retrieval and paste the whole corpus. It's simpler but costs far more per query, and quality degrades on very long inputs. Use prompt caching plus long context for small, stable corpora; RAG for large or changing ones.
  • Permissions: enforce document-level access control at retrieval time. Leaking HR documents through a chatbot is a classic failure.
  • Freshness: incremental re-indexing via change-data-capture from source systems.

Evaluating RAG

Evaluate retrieval and generation separately.

Stage Metric How
Retrieval Recall@k, MRR, NDCG Labelled (question, relevant chunk) pairs
Generation Faithfulness / groundedness Does every claim appear in the retrieved context? (LLM judge)
Generation Answer correctness Compare with reference answers
End to end Task success, citation accuracy, "I don't know" rate Human review of samples

Tools: RAGAS, TruLens, DeepEval, Arize Phoenix, LangSmith, Braintrust. Build a golden dataset of 100–300 real questions first; it is the most valuable asset in any RAG project.

Build it

Project 3: "The chatbot makes things up about our docs"

Business problem: a company's support bot answers from its documentation but hallucinates policies, and customers screenshot the wrong answers.

  1. Ingest a real docs site (e.g., the Kubernetes or Stripe docs) with structure-aware chunking.
  2. Build a golden set of 150 questions with the correct source section for each.
  3. Compare: dense-only, BM25-only, hybrid, hybrid + reranker, + contextual chunking. Report Recall@5 for each.
  4. Add grounding instructions and a faithfulness judge; measure hallucination rate before and after.
  5. Deliverable: a dashboard of retrieval recall, faithfulness and cost per query, plus the configuration you'd ship.
