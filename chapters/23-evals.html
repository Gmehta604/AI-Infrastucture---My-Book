Evaluation and Observability

You cannot improve what you cannot measure, and LLM systems are unusually hard to measure: outputs are open-ended, non-deterministic and change whenever a prompt, model version or retrieval index changes. Mature AI teams treat evals like tests and traces like logs. This chapter shows how.

Three kinds of evaluation

Kind Question Examples
Capability benchmarks How good is the model in general? MMLU-Pro, GPQA Diamond, AIME, SWE-bench, Humanity's Last Exam, ARC-AGI, LMArena
Application evals Does my system do my task well? Your golden datasets, rubrics, task success rates
Online / production metrics Is it working for real users right now? Thumbs up/down, resolution rate, escalations, latency, cost

Public benchmarks help choose candidate models. Only application evals tell you what to ship.

Why public benchmarks mislead

  • Contamination: test questions leak into training data.
  • Saturation: once top models score 90%+, the benchmark stops distinguishing them.
  • Mismatch: your task isn't multiple-choice trivia.
  • Harness sensitivity: prompt format, number of attempts, and tool access change scores by many points. Compare only numbers run under the same harness.
  • Arena gaming: preference leaderboards reward style (length, formatting) as well as substance.

Building application evals

Graders, from most to least reliable

  1. Deterministic code checks: exact match, regex, JSON schema validity, unit tests passing, SQL returns the right rows.
  2. Reference comparison: similarity to a gold answer, or an LLM judge comparing with the gold answer.
  3. LLM-as-judge with a rubric: a strong model scores against explicit criteria.
  4. Human review: gold standard, slow and expensive; use it to calibrate the judges.
import json
from openai import OpenAI
client = OpenAI()

RUBRIC = """You are grading a customer-support answer.
Score each criterion 1 (pass) or 0 (fail):
- correct: the answer agrees with the reference answer on all facts
- grounded: every claim is supported by the provided context
- complete: it addresses every part of the question
- tone: polite and concise
Return JSON: {"correct":0|1,"grounded":0|1,"complete":0|1,"tone":0|1,"reason":"..."}"""

def judge(question, context, reference, answer, model="gpt-5.5-mini"):
    msg = f"{RUBRIC}\n\nQuestion: {question}\nContext: {context}\nReference: {reference}\nAnswer: {answer}"
    out = client.chat.completions.create(model=model, temperature=0,
            response_format={"type": "json_object"},
            messages=[{"role": "user", "content": msg}])
    return json.loads(out.choices[0].message.content)

def run_eval(system, dataset):
    rows = []
    for ex in dataset:
        ans, ctx = system(ex["question"])
        rows.append({**judge(ex["question"], ctx, ex["reference"], ans), "category": ex["category"]})
    for key in ["correct", "grounded", "complete", "tone"]:
        print(key, sum(r[key] for r in rows) / len(rows))
    return rows

(Model names are placeholders; use whatever judge model you have access to.)

LLM-judge pitfalls: position bias (prefers the first option; randomise order), verbosity bias (prefers longer answers), self-preference (prefers its own family's style). Use binary or low-cardinality scores with explicit criteria, and measure judge agreement with humans on 50–100 examples before trusting it.

Statistics matter

With 100 examples, a pass rate of 80% has a 95% confidence interval of roughly ±8 points. Don't celebrate a 2-point improvement on 100 examples. For non-deterministic agents, run each task several times and report pass@1 averaged, plus pass^k (succeeds on all k tries) for reliability.

Evals in CI

Treat prompts, retrieval settings and model versions like code. On every change, run the eval suite and block merges that regress.

# .github/workflows/llm-evals.yml
name: llm-evals
on: [pull_request]
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: python evals/run.py --dataset evals/golden.jsonl --out results.json
        env: { OPENAI_API_KEY: "${{ secrets.OPENAI_API_KEY }}" }
      - run: python evals/compare.py --baseline evals/baseline.json --current results.json --max-drop 0.02

Tools: promptfoo, Braintrust, LangSmith, Arize Phoenix, DeepEval, Inspect (UK AI Security Institute; widely used for safety and capability evals), OpenAI Evals.

Observability: tracing LLM systems

A single user request in an agentic RAG system may involve a query rewrite, three searches, a rerank, two model calls and four tool calls. When the answer is wrong or slow, you need the trace.

Use OpenTelemetry with the GenAI semantic conventions (gen_ai.request.model, gen_ai.usage.input_tokens, etc.) so traces flow to any backend: Langfuse, Arize Phoenix, LangSmith, Datadog, Honeycomb, Grafana Tempo.

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

trace.set_tracer_provider(TracerProvider())
trace.get_tracer_provider().add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))
tracer = trace.get_tracer("rag-service")

def traced_llm_call(model, messages):
    with tracer.start_as_current_span("chat " + model) as span:
        span.set_attribute("gen_ai.request.model", model)
        resp = client.chat.completions.create(model=model, messages=messages)
        span.set_attribute("gen_ai.usage.input_tokens", resp.usage.prompt_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", resp.usage.completion_tokens)
        return resp

What to monitor in production

Layer Metrics
Serving TTFT, TPOT, p95/p99 latency, error rates, queue depth, GPU utilisation, KV cache usage, prefix-cache hit rate
Cost Tokens and $ per request, per feature, per customer; cost anomalies
Quality Online judge scores on sampled traffic, user feedback, refusal rate, "I don't know" rate, escalation to humans
Safety Prompt-injection detections, PII leaks, policy violations
Drift Changes in input topics or length distributions; provider model version changes
Build it

Project 6: "A prompt change broke production and nobody noticed"

Business problem: a team edited a system prompt; answer accuracy on refund questions silently dropped for two weeks.

  1. Take your RAG system from Chapter 21. Create a 200-example golden set with categories.
  2. Add OpenTelemetry tracing with Langfuse or Phoenix; build a dashboard of cost, latency and judge scores.
  3. Wire the eval suite into GitHub Actions with a regression threshold.
  4. Demonstrate: introduce a subtle prompt regression in a pull request and show CI blocking it, with the failing category highlighted.
