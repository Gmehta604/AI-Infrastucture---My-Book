Pretraining and Scaling Laws

Pretraining is where a model learns almost everything it knows: grammar, facts, reasoning patterns, code. It is also where most of the money goes. This chapter covers the data pipeline, the scaling laws that decide how big a model to train, and what a frontier-scale training run actually looks like.

The objective

Pretraining is next-token prediction on a huge corpus, minimising cross-entropy. Nothing more. Capabilities like translation, summarisation and coding emerge because predicting text well requires them.

Key facts:

  • Scale: Llama 3 trained on about 15 trillion tokens (2024); DeepSeek-V3 on 14.8T; Qwen3 on about 36T (2025). Frontier 2026 runs are believed to use tens of trillions of tokens, a rising share of which is synthetic.
  • Quality beats quantity: Hugging Face's FineWeb-Edu showed that keeping only web pages a classifier rates as "educational" improves models dramatically per token.
  • Deduplication matters because repeated text wastes compute and encourages memorisation.
  • Decontamination removes benchmark questions from training data so evaluations stay honest.
  • Data mixture is tuned with small proxy models, then the best mixture is used at full scale. Code and math data improve reasoning even for non-code tasks.
  • Annealing / mid-training: at the end of pretraining, the learning rate decays while the mix shifts toward the highest-quality data (curated math, code, reasoning traces, long documents).

Infrastructure of data

Data processing for a frontier run is a big-data job in its own right: petabytes of raw crawl processed with Spark, Ray Data, Dask or custom Rust tooling on thousands of CPU cores; stored as sharded Parquet or custom binary formats on object storage; and streamed to GPUs fast enough to never stall them. Hugging Face's datatrove and NVIDIA's NeMo Curator are open-source examples.

# Packing documents into fixed-length training sequences
import numpy as np
def pack(token_docs, seq_len, eos_id):
    buf = []
    for doc in token_docs:
        buf.extend(doc + [eos_id])
        while len(buf) >= seq_len + 1:
            chunk, buf = buf[:seq_len + 1], buf[seq_len:]
            yield np.array(chunk[:-1]), np.array(chunk[1:])   # inputs, targets

Scaling laws

In 2020, Kaplan et al. at OpenAI found that loss falls as a power law in parameters N, data D, and compute C, smoothly across many orders of magnitude. In 2022, Hoffmann et al. at DeepMind (Chinchilla) refitted the laws and found the compute-optimal recipe:

L(N, D) = E + A / N^α + B / D^β (α ≈ 0.34, β ≈ 0.28 in the Chinchilla fit) Compute C ≈ 6 · N · D Compute-optimal: D ≈ 20 · N tokens

Meaning: with a fixed budget, grow parameters and data together. Chinchilla (70B params, 1.4T tokens) beat Gopher (280B params, 300B tokens) using the same compute.

def chinchilla_optimal(C):
    # C = 6 N D and D = 20 N  ->  C = 120 N^2
    N = (C / 120) ** 0.5
    return N, 20 * N

for C in [1e21, 1e23, 1e25, 1e26]:
    N, D = chinchilla_optimal(C)
    print(f"C={C:.0e}: N={N/1e9:7.1f}B params, D={D/1e12:6.2f}T tokens")

"Overtraining" for inference economics

Chinchilla-optimal minimises training cost. But a model that will serve billions of requests should be smaller and trained longer, because inference cost scales with parameters. Llama 3 8B was trained on 15T tokens, about 1,875 tokens per parameter, almost 100× past Chinchilla-optimal. This is the norm now: small models are "overtrained" deliberately.

Key idea. Total cost = training cost + (inference cost per token × tokens served over the model's life). For popular models, inference dominates, so labs trade extra training compute for a smaller, cheaper-to-serve model.

Emergent abilities and predictability

Some abilities appear to switch on suddenly at scale ("emergence"), though later work showed that with smoother metrics, many improve gradually. Labs now predict the final loss of big runs from small runs with high accuracy. Predicting specific downstream capabilities remains harder, which is a core problem for safety evaluations.

The three scaling axes (2024–2026)

By 2025, the industry spoke of three scaling laws. Pretraining gains continued but became more expensive per step of improvement; RL scaling and test-time compute (Chapters 12–13) delivered the biggest jumps in reasoning and agentic ability. In 2026, the labs' biggest compute budgets are split between very large pretraining runs and very large RL runs.

Anatomy of a frontier training run

Item Order of magnitude (2025–2026 frontier)
Training compute 10²⁵–10²⁷ FLOPs
GPUs 20,000–200,000+ accelerators (H100/H200, B200/GB200/GB300, TPU, Trainium)
Duration 1–4 months of pretraining, plus months of post-training
Power 50–500+ MW for the cluster
Cost of compute Hundreds of millions to billions of dollars
Team Hundreds of researchers and engineers

A detail that surprises newcomers: reliability is a first-class problem. At 100,000 GPUs, hardware fails constantly. Meta reported 419 unexpected interruptions during a 54-day Llama 3 405B run on 16,384 H100s, roughly one every three hours, mostly GPU and HBM failures. The infrastructure must detect failures, drain bad nodes, restore from checkpoints and resume in minutes. Goodput (the fraction of time spent making real progress) is a headline metric.

Metrics to watch during a run

  • Training and validation loss (smooth downward curve; spikes are warnings).
  • Gradient norm (sudden growth predicts spikes).
  • Tokens per second and MFU: model FLOPs utilisation, the fraction of peak hardware FLOPs doing useful model math. 35–50% is good for large dense models; MoE runs are often lower.
  • Downstream evals on intermediate checkpoints (MMLU-style knowledge, GSM8K-style math, HumanEval-style code).
  • Goodput and time lost to failures.
Build it

Project: Train a small GPT and measure MFU

Business problem: a team wants to know whether a custom small model for their domain is affordable.

  1. Train a ~125M-parameter GPT on 2–10B tokens of FineWeb-Edu using Karpathy's nanoGPT or nanochat, or the modded-nanogpt speedrun repository, on a rented 8×H100 node.
  2. Log tokens/sec and compute MFU = (6 · N · tokens/sec) / (GPUs × peak FLOP/s).
  3. Try torch.compile, BF16 vs FP32, and FlashAttention on/off. Record each change's effect.
  4. Deliverable: a table of "cost to train to loss X" and a projection of what a 1B model on 50B tokens would cost.
