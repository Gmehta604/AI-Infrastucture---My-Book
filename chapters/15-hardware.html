GPUs and AI Accelerators

Every question in AI infrastructure eventually becomes a hardware question: will it fit in memory, is it compute-bound or bandwidth-bound, how fast can chips talk to each other? This chapter gives you the mental model of a GPU and a tour of the 2026 accelerator landscape.

Why GPUs?

A CPU has a few dozen powerful cores optimised for low-latency, branchy, sequential code. A GPU has thousands of simpler cores optimised for throughput on the same operation applied to lots of data, which is exactly what matrix multiplication is.

The memory hierarchy (the part that matters most)

Level Size (H100) Bandwidth Latency
Registers ~256 KB per SM Highest ~1 cycle
Shared memory / L1 up to 228 KB per SM ~tens of TB/s aggregate ~30 cycles
L2 cache 50 MB ~10 TB/s-class ~200 cycles
HBM (device memory) 80 GB 3.35 TB/s ~500+ cycles
NVLink (other GPU) — 900 GB/s microseconds
PCIe / network — 64 GB/s / 50 GB/s microseconds

Every fast kernel is about keeping data in the upper levels and avoiding trips to HBM. FlashAttention (Chapter 16) is the canonical example.

Tensor Cores

Tensor Cores execute small matrix multiply-accumulates (e.g., 16×16 tiles) in one instruction. On an H100, they deliver about 989 TFLOP/s in dense BF16, versus about 67 TFLOP/s from regular FP32 CUDA cores. If your math isn't running on tensor cores, you are using 7% of the chip. Each generation adds lower precisions: FP8 in Hopper, FP4 in Blackwell.

The roofline model: compute-bound vs memory-bound

Every operation has an arithmetic intensity: FLOPs performed per byte moved from memory.

Attainable FLOP/s = min( Peak FLOP/s , Memory bandwidth × Arithmetic intensity ) Ridge point (H100 BF16) = 989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOPs per byte
  • Below ~295 FLOPs/byte, the operation is memory-bound: the chip waits on memory.
  • Above it, compute-bound: the math units are the limit.
def intensity_matmul(M, N, K, bytes_per=2):
    flops = 2 * M * N * K
    bytes_moved = bytes_per * (M * K + K * N + M * N)
    return flops / bytes_moved

# Decode: one token (M=1) times a 4096x4096 weight
print(intensity_matmul(1, 4096, 4096))     # ≈ 1 FLOP/byte  -> badly memory-bound
# Batch of 256 tokens
print(intensity_matmul(256, 4096, 4096))   # ≈ 228          -> near the ridge
# Prefill of 4096 tokens
print(intensity_matmul(4096, 4096, 4096))  # ≈ 1365         -> compute-bound

This single calculation explains why batching is the most important idea in LLM serving (Chapter 19), and why decode speed tracks memory bandwidth rather than FLOPs.

Rack-scale systems are the 2025–26 unit of compute. A GB200/GB300 NVL72 rack connects 72 GPUs with NVLink switches so they behave like one giant GPU with ~13–20 TB of HBM, drawing around 120–140 kW with liquid cooling. NVIDIA's roadmap continues with Rubin CPX (a GDDR7-based chip specialised for the compute-heavy prefill phase, late 2026), Rubin Ultra in the Kyber NVL576 rack (2027, ~600 kW per rack) and Feynman (2028). NVIDIA also licensed Groq's technology and folded a Groq-derived low-latency decode accelerator (LPX) into the Rubin platform.

Why NVIDIA still dominates: CUDA and its libraries (cuBLAS, cuDNN, NCCL, TensorRT), the NVLink/NVSwitch scale-up fabric, InfiniBand and Spectrum-X networking (from the Mellanox acquisition), and supply-chain scale. Competitors win where customers can afford to port software (hyperscalers, big labs) or where memory capacity per dollar matters most.

Interconnects: scale-up and scale-out

  • Scale-up (NVLink, AMD Infinity Fabric / UALink, Google ICI): very high bandwidth among a few dozen to a few hundred chips. Tensor and expert parallelism live here.
  • Scale-out (InfiniBand, RoCE Ethernet, Ultra Ethernet): connects thousands of nodes. Data and pipeline parallelism cross it. Rail-optimised, non-blocking fat-tree topologies are standard.
  • Collectives (all-reduce, all-gather, reduce-scatter, all-to-all) run over these via NCCL / RCCL (Chapter 17).

Memory capacity arithmetic you should do reflexively

def gb(params_b, bytes_per_param):
    return params_b * bytes_per_param           # billions of params × bytes = GB

print("Llama-70B BF16 weights:", gb(70, 2), "GB")          # 140 GB -> 2x H100 minimum
print("70B FP8:", gb(70, 1), "GB; 4-bit:", gb(70, 0.5), "GB")
print("70B full training (~16 B/param):", gb(70, 16), "GB") # 1,120 GB -> must shard
print("DeepSeek-V3 671B FP8 weights:", gb(671, 1), "GB")    # 671 GB -> e.g., 8x H200 (1,128 GB)

Useful commands

nvidia-smi                          # utilisation, memory, power, temperature
nvidia-smi topo -m                  # how GPUs connect (NVLink vs PCIe)
nvidia-smi dmon -s pucvmet          # live per-second telemetry
nvidia-smi -q -d ECC                # memory error counts (failing HBM shows up here)
dcgmi diag -r 3                     # NVIDIA DCGM health diagnostics

A warning: nvidia-smi "GPU-Util" only means a kernel was running, not that tensor cores were busy. A GPU can show 100% utilisation at 10% of its FLOPs. Use MFU, DCGM's SM_ACTIVE / TENSOR_ACTIVE metrics, or a profiler.
