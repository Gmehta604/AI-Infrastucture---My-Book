Fine-Tuning in Practice

Most companies will never pretrain a model, but many will fine-tune one. This chapter covers when to fine-tune (and when not to), parameter-efficient methods like LoRA and QLoRA, the memory math, and how fine-tuned models are served at scale.

First: should you fine-tune at all?

Good reasons to fine-tune: - Cost and latency: replace a frontier model with a fine-tuned 3–8B model for one narrow, high-volume task (often 10–50× cheaper). - Consistent format or style that prompts can't reliably hold. - Domain language (legal, medical, internal code). - Data residency / on-prem needs, using an open model.

Bad reasons: teaching the model frequently-changing facts (use RAG), or fixing problems a better prompt would solve.

Full fine-tuning vs parameter-efficient fine-tuning (PEFT)

Full fine-tuning updates every weight: best quality ceiling, but needs ~16 bytes/parameter of memory and produces a full model copy per task.

LoRA (Low-Rank Adaptation, 2021) freezes the original weights and learns a small update for selected matrices as the product of two thin matrices:

W' = W + (α / r) · B · A W: d×k (frozen) B: d×r A: r×k with r ≪ d (e.g., r = 16)

For a 4096×4096 matrix at r=16, LoRA trains 131K parameters instead of 16.8M, under 1%. B starts at zero, so training begins exactly at the original model.

import torch, torch.nn as nn, math

class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=16, alpha=32, dropout=0.05):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False
        self.A = nn.Parameter(torch.empty(r, base.in_features))
        self.B = nn.Parameter(torch.zeros(base.out_features, r))
        nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))
        self.scale, self.drop = alpha / r, nn.Dropout(dropout)

    def forward(self, x):
        return self.base(x) + (self.drop(x) @ self.A.T @ self.B.T) * self.scale

    @torch.no_grad()
    def merge(self):                       # fold the adapter in for zero-overhead serving
        self.base.weight += (self.B @ self.A) * self.scale
        return self.base

QLoRA

QLoRA (2023) stores the frozen base model in 4-bit NF4 and trains LoRA adapters in BF16 on top. It made fine-tuning a 65B model possible on a single 48 GB GPU.

Memory comparison for an 8B model (approximate)

Method Weights Grads + optimizer Fits on
Full FT (BF16 + AdamW) 16 GB ~112 GB 2–4× 80 GB GPUs with FSDP
LoRA (BF16 base) 16 GB < 1 GB one 24–40 GB GPU
QLoRA (4-bit base) ~5 GB < 1 GB one 12–16 GB GPU

Plus activations, which depend on sequence length and batch size (reduce with gradient checkpointing).

A real fine-tuning script

# pip install transformers peft trl datasets bitsandbytes accelerate
import torch
from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig
from trl import SFTTrainer, SFTConfig

model_id = "Qwen/Qwen2.5-7B-Instruct"          # any open instruct model
tok = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    quantization_config=BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                                           bnb_4bit_compute_dtype=torch.bfloat16),
    torch_dtype=torch.bfloat16, device_map="auto")

# each row: {"messages": [{"role": "user", ...}, {"role": "assistant", ...}]}
ds = load_dataset("json", data_files="train.jsonl", split="train")

peft_cfg = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, task_type="CAUSAL_LM",
                      target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                                      "gate_proj", "up_proj", "down_proj"])
args = SFTConfig(output_dir="out", num_train_epochs=2, per_device_train_batch_size=4,
                 gradient_accumulation_steps=4, learning_rate=2e-4, lr_scheduler_type="cosine",
                 warmup_ratio=0.03, bf16=True, gradient_checkpointing=True,
                 logging_steps=10, max_length=2048, assistant_only_loss=True)
trainer = SFTTrainer(model=model, args=args, train_dataset=ds,
                     processing_class=tok, peft_config=peft_cfg)
trainer.train()
trainer.save_model("out/adapter")

Library APIs change often; check the TRL and PEFT docs for current argument names. Unsloth offers 2× faster single-GPU fine-tuning with lower memory, and Axolotl and LLaMA-Factory wrap all of this in YAML configs.

Practical rules

  1. Data quality over quantity. 500–5,000 clean, diverse, representative examples usually beat 100,000 noisy ones.
  2. Hold out an eval set that mirrors production traffic, and write the eval before training.
  3. Learning rate for LoRA: 1e-4 to 3e-4. For full fine-tuning: 1e-5 to 5e-5.
  4. 1–3 epochs. More causes overfitting and catastrophic forgetting of general skills.
  5. Use the model's own chat template exactly. Mismatched templates are the most common silent failure.
  6. Check for regressions on general benchmarks and safety behaviour after tuning.

Serving many fine-tunes: multi-LoRA

A company with 500 customers, each with their own fine-tune, cannot run 500 model copies. Because LoRA adapters are small (tens of MB), a server can keep one base model on the GPU and apply different adapters per request in the same batch. Systems: S-LoRA, Punica, LoRAX, and built-in multi-LoRA support in vLLM and SGLang.

vllm serve Qwen/Qwen2.5-7B-Instruct --enable-lora \
  --lora-modules customer_a=/adapters/a customer_b=/adapters/b --max-loras 16
# then call the OpenAI-compatible API with model="customer_a"

Managed fine-tuning

OpenAI, Google, Amazon Bedrock, Together, Fireworks and others offer fine-tuning APIs, including reinforcement fine-tuning with custom graders. Thinking Machines Lab's Tinker (2025) provides an API for low-level LoRA training loops on open models while hiding the cluster. Trade-offs versus self-hosting: less control and vendor lock-in versus no infrastructure to run.

Project: Replace an expensive API call with a fine-tuned small model

Business problem: a company classifies and routes 2 million support tickets per month with a frontier model, costing tens of thousands of dollars a month.

  1. Use the frontier model to label 5,000 tickets (distillation data). Hand-check 300 for a gold eval set.
  2. QLoRA fine-tune a 3B–8B model. Evaluate accuracy on the gold set vs. the frontier model.
  3. Serve it with vLLM on one GPU; load test with realistic traffic.
  4. Deliverable: accuracy difference, p95 latency, and monthly cost comparison including GPU rental. Include the break-even volume at which self-hosting wins.
