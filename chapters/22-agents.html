Agents, Tools and MCP

An agent is a model that acts: it calls tools, observes results and decides what to do next, in a loop, until a goal is met. Coding agents, research agents and computer-use agents went from demos in 2024 to major products in 2025–26. Agents also create the hardest infrastructure problems of the moment: long-running sessions, sandboxes, huge token volumes and new security risks.

The agent loop

That is the entire idea. The quality of an agent comes from (1) the model's judgement, (2) the tools and their descriptions, (3) the context you give it, and (4) the harness that runs the loop safely.

Tool calling

Models are trained to emit structured tool calls when given tool definitions (name, description, JSON Schema for arguments). Your code executes the call and returns the result.

import json, subprocess, anthropic

client = anthropic.Anthropic()
tools = [
    {"name": "run_python",
     "description": "Execute Python code in a sandbox and return stdout/stderr. Use for calculations and data analysis.",
     "input_schema": {"type": "object", "properties": {"code": {"type": "string"}}, "required": ["code"]}},
    {"name": "read_file",
     "description": "Read a UTF-8 text file from the working directory.",
     "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}},
]

def execute(name, args):
    if name == "run_python":        # in production: an isolated container / microVM, not subprocess
        p = subprocess.run(["python3", "-c", args["code"]], capture_output=True, text=True, timeout=30)
        return (p.stdout + p.stderr)[-4000:]
    if name == "read_file":
        return open(args["path"]).read()[:8000]
    return f"unknown tool {name}"

def agent(goal, model="claude-opus-5-5", max_steps=20):
    messages = [{"role": "user", "content": goal}]
    for step in range(max_steps):
        resp = client.messages.create(model=model, max_tokens=4096, tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")
        results = []
        for block in resp.content:
            if block.type == "tool_use":
                out = execute(block.name, block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
        messages.append({"role": "user", "content": results})
    return "Stopped: step limit reached."

print(agent("What is the 50th Fibonacci number? Verify by computing it."))

The OpenAI, Google and open-model APIs follow the same pattern with different field names. Frameworks such as the Claude Agent SDK, OpenAI Agents SDK, LangGraph, Google ADK, CrewAI, Pydantic AI, smolagents and Mastra wrap it with state management, streaming and multi-agent orchestration.

The Model Context Protocol (MCP)

Before MCP, every app wrote custom integrations for every tool. MCP (introduced by Anthropic in November 2024, adopted by OpenAI, Google, Microsoft and most of the industry in 2025, and donated to a Linux Foundation-hosted foundation in late 2025) standardises how applications expose tools, resources (data) and prompts to models.

# A minimal MCP server with the official Python SDK:  pip install "mcp[cli]"
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("gpu-inventory")

GPUS = {"node-01": {"gpu": "H100", "free": 3}, "node-02": {"gpu": "B200", "free": 0}}

@mcp.tool()
def free_gpus(gpu_type: str | None = None) -> dict:
    """Return nodes with free GPUs, optionally filtered by GPU type (e.g. 'H100')."""
    return {n: v for n, v in GPUS.items() if v["free"] > 0 and (gpu_type is None or v["gpu"] == gpu_type)}

@mcp.resource("inventory://all")
def inventory() -> str:
    """Full GPU inventory as JSON."""
    import json; return json.dumps(GPUS)

if __name__ == "__main__":
    mcp.run()          # stdio transport; clients like Claude Code or Claude Desktop can connect

Related standards: Agent Skills (packaged instructions and scripts an agent loads on demand), A2A (Google's agent-to-agent protocol), and the OpenAI-originated AGENTS.md convention for repository instructions.

Context engineering

For long tasks, the context window is the agent's working memory and the main thing to manage.

  • Keep tool outputs small: return summaries, paginate, truncate.
  • Compaction: summarise old turns when nearing the limit.
  • External memory: write notes, plans and progress to files the agent can re-read (a to-do list is surprisingly powerful).
  • Sub-agents: delegate a search or investigation to a fresh context and receive only the conclusion.
  • Just-in-time retrieval: give the agent tools to look things up (grep, search) instead of stuffing everything in up front.
  • Cache-friendly structure: keep the system prompt and tool definitions stable so prompt caching works; agents re-send their whole context every step.

Agent infrastructure problems

  1. Sandboxing. Agents run code and touch files. Use isolated containers or microVMs (Firecracker, gVisor, Kata) with no default network access, resource limits and snapshotting. E2B, Modal, Daytona and cloud providers sell this as a service.
  2. Token volume. A single coding task can consume 1–20M tokens (mostly re-read context). Prompt caching and prefix-cache-aware routing are essential for cost.
  3. Durability. Tasks last minutes to hours. Use durable execution (Temporal, Inngest, Restate, or queue plus checkpoints) so a crash doesn't lose progress.
  4. Observability. Trace every step, tool call and token (Chapter 23).
  5. Evaluation. Agents are non-deterministic; measure success rates over many runs on realistic tasks (SWE-bench Verified/Pro, Terminal-Bench, τ²-bench, OSWorld, GAIA, BrowseComp).

Security: the lethal trifecta

Simon Willison's framing: an agent is dangerous when it has (1) access to private data, (2) exposure to untrusted content, and (3) a way to communicate externally. Prompt injection (malicious instructions hidden in a web page, email or document) can then make it exfiltrate data.

Defences, in layers: least-privilege tools; separate the model that reads untrusted content from the one holding secrets (the "dual LLM" and CaMeL patterns); allow-lists for network egress; human confirmation for irreversible actions; classifiers for injection; and logging for audit. There is no complete fix yet; design systems so a successful injection can do limited damage.

Build it

Project: An on-call assistant for a GPU cluster

Business problem: ML engineers wait hours for the platform team to diagnose failed training jobs ("NCCL timeout", "CUDA OOM", "node unhealthy").

  1. Build MCP servers exposing read-only tools: job logs, kubectl describe, DCGM metrics, a runbook search (RAG over your runbooks).
  2. Write an agent that, given a failed job ID, gathers evidence and proposes a diagnosis and fix, citing log lines.
  3. Evaluate on 30 historical incidents (or ones you create by injecting faults into a test cluster): diagnosis accuracy, time, tokens.
  4. Add guardrails: no write actions without human approval; redact secrets from logs before they reach the model.
