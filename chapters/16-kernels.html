The Software Stack: CUDA, Triton, Kernels and Compilers

Between your PyTorch code and the silicon sits a deep software stack. Knowing it lets you find where time is actually spent and fix it: fuse kernels, pick the right precision, or write a custom kernel when nothing else is fast enough. Kernel engineers are some of the most sought-after people in AI.

The stack

The CUDA programming model in five minutes

You write a kernel, a function that runs on the GPU. You launch it on a grid of thread blocks; each block has up to 1,024 threads. Threads execute in groups of 32 called warps that run in lockstep. Each block runs on one SM and can share fast shared memory.

// vector add in CUDA C++
__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // global thread index
    if (i < n) c[i] = a[i] + b[i];
}
// launch: enough blocks of 256 threads to cover n elements
// add<<<(n + 255) / 256, 256>>>(a, b, c, n);

Rules of performance:

  1. Coalesced memory access: adjacent threads should read adjacent addresses.
  2. Reuse data from shared memory/registers (tiling) instead of re-reading HBM.
  3. Occupancy: enough warps in flight to hide memory latency.
  4. Avoid warp divergence: branches that split a warp serialise.
  5. Use tensor cores via the right data types, shapes (multiples of 8/16/64) and instructions (WMMA, WGMMA on Hopper, tcgen05 on Blackwell).

Kernel fusion: the biggest easy win

Each separate PyTorch op launches a kernel that reads its input from HBM and writes its output back. A chain like y = gelu(x @ W + b) done naively makes several round trips. Fusion does the bias add and GELU while the matmul result is still in registers.

Elementwise ops are memory-bound, so fusing them is nearly free speed.

torch.compile

PyTorch 2's compiler traces your Python (TorchDynamo), builds a graph, and generates fused Triton kernels (TorchInductor). One line often gives 1.3–2× speedups in training and more in inference.

import torch
model = torch.compile(model)                           # default
model = torch.compile(model, mode="max-autotune")      # tries kernel configs, uses CUDA graphs

CUDA graphs record a whole sequence of kernel launches and replay it with one call, removing CPU launch overhead. They matter a lot in LLM decode, where each step is many tiny kernels.

Triton: GPU kernels in Python

Triton (OpenAI, 2021) lets you write block-level GPU kernels in Python; the compiler handles thread-level details, memory coalescing and shared memory. It is the practical entry point to kernel writing.

import torch, triton, triton.language as tl

@triton.jit
def softmax_kernel(out_ptr, in_ptr, stride, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)                               # one program per row
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(in_ptr + row * stride + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)                            # stability
    num = tl.exp(x)
    y = num / tl.sum(num, axis=0)
    tl.store(out_ptr + row * stride + cols, y, mask=mask)

def softmax(x):
    n_rows, n_cols = x.shape
    out = torch.empty_like(x)
    BLOCK = triton.next_power_of_2(n_cols)
    softmax_kernel[(n_rows,)](out, x, x.stride(0), n_cols, BLOCK=BLOCK)
    return out

x = torch.randn(4096, 1024, device="cuda")
assert torch.allclose(softmax(x), torch.softmax(x, dim=1), atol=1e-6)

This fused softmax reads each row from HBM once and writes once, versus several passes for a naive implementation. Newer options include CuTe DSL (Python for CUTLASS), ThunderKittens, TileLang and Helion.

FlashAttention: the most important kernel of the decade

Standard attention materialises the T×T score matrix in HBM. For T=32,000 that is a billion entries per head, far too much memory and bandwidth.

FlashAttention (Tri Dao, 2022) never materialises it. It tiles Q, K and V into blocks that fit in shared memory and computes softmax incrementally with the "online softmax" trick, keeping a running max and running sum per row and rescaling as each new block arrives.

import torch
def online_softmax_attention(q, K, V, block=128):
    # q: (d,), K, V: (T, d). Processes K/V in blocks, never storing all scores.
    m, l = torch.tensor(-float("inf")), torch.tensor(0.0)
    acc = torch.zeros_like(V[0])
    for s in range(0, K.shape[0], block):
        scores = K[s:s + block] @ q / q.shape[0] ** 0.5
        m_new = torch.maximum(m, scores.max())
        scale = torch.exp(m - m_new)                  # rescale old accumulators
        p = torch.exp(scores - m_new)
        l = l * scale + p.sum()
        acc = acc * scale + p @ V[s:s + block]
        m = m_new
    return acc / l

q, K, V = torch.randn(64), torch.randn(1000, 64), torch.randn(1000, 64)
ref = torch.softmax(K @ q / 8, 0) @ V
print(torch.allclose(online_softmax_attention(q, K, V), ref, atol=1e-5))  # True

Results: memory linear in sequence length instead of quadratic, 2–4× faster, and long context became practical. FlashAttention-2 improved parallelism; FlashAttention-3 (2024) used Hopper's asynchronous TMA and warp specialisation and FP8; FlashAttention-4 (2025) targets Blackwell. For inference, FlashInfer and FlashMLA provide attention kernels over paged KV caches.

Low-precision training: FP8 and beyond

FP8 doubles tensor-core throughput over BF16 and halves memory traffic. The challenge is range: FP8 E4M3 represents only about ±448. Solutions:

  • Per-tensor scaling (NVIDIA Transformer Engine): track the max absolute value and scale into range.
  • Fine-grained block scaling (DeepSeek-V3): a scale per 1×128 activation tile and 128×128 weight block, with higher-precision accumulation. DeepSeek trained V3 almost entirely in FP8.
  • Microscaling formats (MXFP8, MXFP4, NVFP4): hardware-supported block scales on Blackwell. NVFP4 uses a scale per 16 values.

Profiling: measure before optimising

from torch.profiler import profile, ProfilerActivity, schedule

with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             schedule=schedule(wait=1, warmup=1, active=3),
             on_trace_ready=torch.profiler.tensorboard_trace_handler("./trace"),
             record_shapes=True, with_stack=True) as prof:
    for step in range(5):
        train_step()
        prof.step()
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))

Then open the trace in Perfetto or TensorBoard. Tools to know: Nsight Systems (timeline across CPU, GPU, NCCL), Nsight Compute (deep dive into one kernel's memory and compute efficiency), and PyTorch's memory snapshot tool for out-of-memory debugging.

Common findings: - GPU idle gaps waiting for the data loader (fix: more workers, pinned memory, prefetching). - Many tiny kernels with CPU launch overhead (fix: torch.compile, CUDA graphs). - Communication not overlapped with compute (fix: FSDP prefetch, bucket sizes, Chapter 17). - Matmul shapes not multiples of 64/128 (fix: pad vocab size, hidden sizes).
