Training Deep Networks Well

Knowing backprop is not the same as training a large network successfully. This chapter covers the practical toolkit: optimizers, initialisation, normalisation, learning-rate schedules, regularisation and mixed precision. Every modern LLM training run uses all of them.

A complete, modern training loop

Keep this template; later chapters extend it.

import torch, torch.nn as nn, torch.nn.functional as F
from torch.utils.data import DataLoader, TensorDataset
import math

device = "cuda" if torch.cuda.is_available() else "cpu"
X, y = torch.randn(10_000, 128), torch.randint(0, 10, (10_000,))
loader = DataLoader(TensorDataset(X, y), batch_size=256, shuffle=True)

model = nn.Sequential(
    nn.Linear(128, 512), nn.LayerNorm(512), nn.GELU(), nn.Dropout(0.1),
    nn.Linear(512, 10),
).to(device)

opt = torch.optim.AdamW(model.parameters(), lr=3e-4, betas=(0.9, 0.95), weight_decay=0.1)
total_steps, warmup = 20 * len(loader), 200

def lr_at(step):                        # linear warmup + cosine decay
    if step < warmup:
        return step / warmup
    p = (step - warmup) / (total_steps - warmup)
    return 0.1 + 0.9 * 0.5 * (1 + math.cos(math.pi * p))
sched = torch.optim.lr_scheduler.LambdaLR(opt, lr_at)

step = 0
for epoch in range(20):
    for xb, yb in loader:
        xb, yb = xb.to(device), yb.to(device)
        with torch.autocast(device_type=device, dtype=torch.bfloat16, enabled=device == "cuda"):
            loss = F.cross_entropy(model(xb), yb)
        opt.zero_grad(set_to_none=True)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)   # gradient clipping
        opt.step(); sched.step(); step += 1
    print(epoch, loss.item(), sched.get_last_lr()[0])

Every line in that loop is explained below.

Optimizers: from SGD to AdamW (and beyond)

SGD (stochastic gradient descent) uses the gradient from a random mini-batch rather than the full dataset. It is noisy but cheap, and the noise can even help generalisation.

Momentum keeps a running average of past gradients, like a ball rolling downhill that builds speed along consistent directions and damps oscillation.

Adam (2014) keeps two running averages per parameter: the mean of gradients (momentum, m) and the mean of squared gradients (v). It divides the step by √v, so each parameter gets its own adaptive learning rate.

m ← β₁m + (1−β₁)g v ← β₂v + (1−β₂)g² w ← w − η · m̂ / (√v̂ + ε) (m̂, v̂ are bias-corrected)

AdamW (2017) applies weight decay directly to the weights rather than through the gradient, which works better. AdamW is the default for LLMs. LLM settings are typically β₁=0.9, β₂=0.95, weight decay 0.1.

Infrastructure consequence: Adam stores m and v for every parameter, usually in FP32. With FP32 master weights, that is 4+4+4 = 12 bytes of optimizer state per parameter, plus 2 bytes of BF16 weights and 2 of gradients: about 16 bytes per parameter. A 70B model needs over 1.1 TB just for this, before activations. This number drives the whole design of ZeRO/FSDP (Chapter 17).

Newer optimizers. Muon (2024), which orthogonalises the momentum matrix for each 2-D weight using Newton–Schulz iterations, was used at scale by Moonshot for Kimi K2 and has become a serious AdamW alternative for hidden-layer matrices. Others include Lion, Sophia, Shampoo and SOAP. AdamW remains the safe default.

Learning rate: the most important hyperparameter

  • Too high: loss explodes or oscillates.
  • Too low: training crawls and may stall.

Warmup starts at a tiny learning rate and ramps up over the first few hundred or thousand steps, because early gradients are large and Adam's variance estimate is unreliable. Cosine decay then lowers it smoothly. WSD (warmup–stable–decay) schedules, popular since 2024, hold the rate constant and decay sharply at the end, which makes it easy to continue training from a checkpoint.

Initialisation

If weights start too large, activations explode layer by layer; too small, they vanish. Xavier/Glorot and Kaiming/He initialisation scale random weights by 1/√(fan-in) so the variance of activations stays roughly constant through depth. GPT-2 additionally scales residual-output projections by 1/√(number of layers).

Normalisation

Normalisation layers rescale activations to have a stable mean and variance.

Layer Normalises over Where
BatchNorm The batch dimension CNNs; awkward for sequences and small batches
LayerNorm The feature dimension of each token Original Transformer, GPT-2
RMSNorm Features, without subtracting the mean Llama, Qwen, DeepSeek; cheaper and just as good

Modern LLMs use pre-norm (normalise the input to each sub-layer) rather than post-norm, because it trains stably at depth. Some add QK-norm (normalising queries and keys) to prevent attention logits from blowing up.

Residual connections

A residual (skip) connection adds a layer's input to its output: x = x + f(x). Gradients flow straight through the addition, so very deep networks train. Every Transformer block has two of them. Think of the model as a "residual stream" that each layer reads from and writes a small update into; interpretability research (Chapter 27) is built on this picture.

Regularisation

  • Weight decay: pulls weights toward zero.
  • Dropout: randomly zeroes activations during training. Common in small models and fine-tuning; usually off in large-scale LLM pretraining, where data is abundant.
  • Data augmentation: flips, crops and noise for images.
  • Early stopping: stop when validation loss stops improving.

Gradient clipping and loss spikes

Large models occasionally produce huge gradients that cause loss spikes. Clipping the global gradient norm to 1.0 is standard. Big training runs still spike; teams keep checkpoints and can roll back a few hundred steps and skip the offending data batch. Handling this automatically is a real infrastructure job.

Mixed precision

Training in BF16 halves memory and doubles speed on tensor cores compared with FP32. The recipe:

  1. Keep an FP32 master copy of weights.
  2. Run the forward and backward passes in BF16.
  3. Do the optimizer update in FP32.
  4. (FP16 only) Multiply the loss by a scale factor so small gradients do not underflow to zero.

torch.autocast does steps 2 and 3 automatically. FP8 training (Chapter 16) pushes this further with per-block scaling factors.

Batch size and gradient accumulation

Larger batches give smoother gradients and better GPU utilisation, up to a critical batch size beyond which returns diminish. LLMs use batches of millions of tokens. If one GPU cannot hold that, you accumulate gradients over several micro-batches before stepping:

accum = 8
for i, (xb, yb) in enumerate(loader):
    loss = F.cross_entropy(model(xb), yb) / accum
    loss.backward()                       # gradients add up
    if (i + 1) % accum == 0:
        opt.step(); opt.zero_grad()

Debugging checklist

  1. Overfit one batch first. If the model cannot drive loss to ~0 on 32 examples, there is a bug.
  2. Check the initial loss. For 10 classes, loss should start near −ln(1/10) ≈ 2.30.
  3. Plot loss, gradient norm, and learning rate every step.
  4. Watch for NaNs. Common causes: learning rate too high, log(0), FP16 overflow.
  5. Log tokens per second and MFU (model FLOPs utilisation) from day one. Those are the infrastructure metrics you will be judged on.
