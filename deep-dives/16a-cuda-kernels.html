CUDA Programming and Kernel Optimisation

This deep dive teaches you to write GPU kernels and, more importantly, to reason about why one kernel is fifty times faster than another that computes the same thing. We take a matrix multiply from a naive version to one that reaches most of cuBLAS's speed, one bottleneck at a time, then cover tensor cores, reductions, CUDA graphs, PyTorch integration, and the tools professionals use to debug and profile kernels.

1. Why learn to write kernels?

Most engineers will call kernels far more often than they write them. Still, kernel knowledge pays off in three ways.

  1. Reading performance correctly. Profiles are lists of kernels. Knowing what a kernel does internally tells you whether 30% of your step time in elementwise_kernel is a problem (usually yes) and how to fix it (usually fusion).
  2. The highest-leverage work in the industry is kernel work. FlashAttention made long-context models practical. DeepSeek's open-sourced DeepGEMM (FP8 matmuls), FlashMLA (attention for its latent-attention architecture) and DeepEP (MoE communication) are a large part of why their models are cheap to train and serve. Each new GPU generation needs new kernels before its hardware features pay off.
  3. Custom fusions for your model. When a production model has an unusual operation (a new activation, a custom attention mask, a quantization format), a fused kernel can cut its cost several times over.

In practice today, you will write most custom kernels in Triton (Deep Dive 16b) and reach for CUDA C++ or CUTLASS/CuTe when you need full control of the hardware. The concepts in this chapter apply to both.

2. The CUDA programming model in code

A CUDA program has two sides: host code that runs on the CPU and device code (kernels) that runs on the GPU. The host allocates GPU memory, copies data, launches kernels and copies results back.

code/16a-cuda-kernels/vector_add.cu (core)

__global__ void vector_add(const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;   // this thread's global index
  if (i < n) c[i] = a[i] + b[i];                   // guard: the last block may overhang
}

// host side
const int threads = 256;
const int blocks = (n + threads - 1) / threads;    // enough blocks to cover n
vector_add<<<blocks, threads>>>(da, db, dc, n);
CUDA_CHECK(cudaGetLastError());                    // launch errors (bad config, etc.)
CUDA_CHECK(cudaMemcpy(hc, dc, bytes, cudaMemcpyDeviceToHost));  // also surfaces runtime errors

Key facts:

  • __global__ marks a kernel: called from the host, runs on the device. __device__ functions are called from device code; __host__ __device__ compiles for both.
  • blockIdx, blockDim, threadIdx and gridDim are built-in 3D coordinates. The global index formula above is the most common line in all of CUDA.
  • Always guard with if (i < n). The grid is rounded up to whole blocks, so the last block usually has threads past the end of the array.
  • Launches are asynchronous. vector_add<<<...>>> returns immediately. Errors inside the kernel appear at the next synchronising call. The CUDA_CHECK macro in common.cuh wraps every API call; skipping it is how people spend a day chasing "wrong results" that were actually an out-of-memory error.

Choosing block and grid sizes

  • Block size: a multiple of 32 (a warp). 128–512 threads is the usual range; 256 is a good default for simple kernels.
  • Grid size: enough blocks to fill every SM several times over, so the scheduler can balance load and hide latency. For simple elementwise kernels, one thread per element is fine.
  • Grid-stride loops decouple the grid from the data size. A fixed number of threads (for example, 8 blocks per SM) walks the whole array, which works for any size and reduces per-block overhead:
__global__ void vector_add_gridstride(const float* a, const float* b, float* c, int n) {
  for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += blockDim.x * gridDim.x)
    c[i] = a[i] + b[i];
}

Vector add reads 8 bytes and writes 4 bytes per FLOP. It is purely memory-bound (Deep Dive 15a), so its speed should approach your GPU's memory bandwidth. ./vector_add prints the achieved GB/s; on an H100 expect roughly 2.8–3.1 TB/s.

2D indexing

For matrices, use a 2D grid and 2D blocks:

dim3 block(16, 16);                                        // 256 threads
dim3 grid((cols + 15) / 16, (rows + 15) / 16);
kernel<<<grid, block>>>(...);
// inside the kernel
int col = blockIdx.x * blockDim.x + threadIdx.x;           // x varies fastest → map it to columns
int row = blockIdx.y * blockDim.y + threadIdx.y;

Map the fastest-varying thread index (x) to the contiguous dimension of your data (columns of a row-major matrix). Getting this backwards is the single most common cause of slow kernels, as kernel 1 below demonstrates.

3. Memory spaces

Space Declared as Scope and lifetime Speed Typical use
Registers Local scalar variables, small fixed-size arrays with constant indexing One thread Fastest Accumulators, loop variables, register tiles
Local memory Arrays indexed dynamically, register spills One thread, but physically in HBM (cached) Slow Avoid; watch for spills
Shared memory __shared__ One thread block ~20–30 cycles Tiles reused by many threads, communication in a block
Global memory cudaMalloc pointers All threads, whole program Slowest on-chip-miss path All inputs and outputs
Constant memory __constant__ (64 KB) All threads, read-only Fast when all threads read the same address Small parameters, lookup tables

Practical rules:

  • Mark pointers const float* __restrict__ when they don't alias. It lets the compiler use the read-only cache and reorder loads.
  • Keep per-thread arrays small and index them with compile-time constants (fully unrolled loops); otherwise they spill to local memory.
  • Global memory accesses should be coalesced and aligned: a warp reading 32 consecutive 4-byte values issues one 128-byte request. Wider per-thread loads (float4, 16 bytes) reduce instruction count further.
  • Pinned (page-locked) host memory (cudaMallocHost) makes host-to-device copies faster and lets them run asynchronously. PyTorch's DataLoader(pin_memory=True) does exactly this.

4. How CUDA code is compiled

  • -arch=sm_90 compiles for H100. A binary containing PTX can be JIT-compiled by the driver for newer GPUs; one containing only SASS runs only on the architecture it was built for. Hopper-specific instructions such as wgmma require sm_90a, and Blackwell's need sm_100a.
  • -lineinfo keeps source line information for profilers without slowing the code.
  • --ptxas-options=-v prints registers, shared memory and spills per kernel. Read this output for every kernel you write.
  • cuobjdump -sass and nvdisasm show the actual machine instructions. Advanced kernel engineers read SASS to confirm the compiler did what they intended (for example, that loads were vectorised).

Here is the ptxas report for this chapter's matmul kernels, compiled for sm_80 (exact numbers vary with compiler version):

1 naive 27 0 none

4 1D block tiling 55 4 KB none
5 2D block tiling 128 8 KB none

Kernels 5 and 6 use four times the registers of kernel 1. With 256 threads per block, that allows only two blocks (16 warps, 25% occupancy) per SM, yet they are by far the fastest. Recall the key idea from 15a: compute-bound kernels trade occupancy for register-level data reuse.

Pitfall

Without #pragma unroll on the small inner loops, an early version of kernels 5 and 6 compiled with 256 bytes of stack per thread: the accumulator array had spilled to local memory. Adding the pragmas removed the spill. Always check the report after a change; a spill can silently halve performance.

5. The matrix-multiply ladder

Matrix multiplication is the ideal teaching kernel: easy to write, extremely hard to make fast, and the operation that dominates AI compute. We compute C = αAB + βC for square FP32 matrices of size 4,096, stored row-major.

FLOPs = 2 × 4096³ ≈ 137 GFLOP Minimum HBM traffic = read A + read B + write C = 3 × 64 MB = 192 MB Best-case intensity ≈ 716 FLOPs per byte → compute-bound on every GPU

So a perfect kernel is limited by arithmetic throughput. Every stage below exists because the previous one moved far more than 192 MB, or kept the arithmetic units waiting.

For reference, here is how a very similar sequence of kernels performed in Simon Boehm's well-known write-up, measured on an RTX A6000 in FP32. Your numbers will differ by GPU, but the shape of the progression is typical.

Stage Idea GFLOP/s % of cuBLAS
1 Naive 309 1.3%
2 Global memory coalescing 1,987 8.5%
3 Shared-memory tiling 2,980 12.8%
4 1D block tiling (several outputs per thread) 8,475 36.5%
5 2D block tiling (register outer product) 15,972 68.7%
6 Vectorised memory access 18,237 78.4%
(beyond) Autotuning, warp tiling 21,779 93.7%
cuBLAS 23,250 100%

./sgemm runs our six kernels on your GPU, checks each against cuBLAS for correctness, and prints the same table.

Kernel 1: naive

One thread per output element, looping over K.

const int row = blockIdx.x * blockDim.x + threadIdx.x;
const int col = blockIdx.y * blockDim.y + threadIdx.y;
if (row < M && col < N) {
  float acc = 0.f;
  for (int k = 0; k < K; ++k) acc += A[row * K + k] * B[k * N + col];
  C[row * N + col] = alpha * acc + beta * C[row * N + col];
}

Bottleneck: uncoalesced access. threadIdx.x varies fastest within a warp and we mapped it to rows. The 32 threads of a warp therefore read A from 32 different rows (addresses K floats apart) and write C to 32 different rows. Each access becomes its own memory transaction. There is also no data reuse: every thread reads a full row of A and column of B from global memory, so the kernel requests 2 × 4096³ × 4 bytes, about 550 GB, for a 137-GFLOP job.

Kernel 2: global memory coalescing

Same algorithm; change only which thread computes which output.

const int row = blockIdx.x * BS + threadIdx.x / BS;
const int col = blockIdx.y * BS + threadIdx.x % BS;

Now the 32 threads of a warp share a row and cover 32 consecutive columns. Reads of B[k*N + col] touch 32 adjacent floats: one 128-byte transaction. Reads of A[row*K + k] are the same address for the whole warp, which the hardware broadcasts. Writes of C are coalesced.

Speed-up: about 6×, from a two-line change. Remaining bottleneck: every thread still streams a full row of A and column of B through the memory system with no reuse.

Kernel 3: shared-memory tiling

Split the computation into tiles. Each 32×32 thread block computes a 32×32 tile of C. It walks along K in steps of 32: the block cooperatively loads a 32×32 tile of A and one of B into shared memory, synchronises, and every thread then computes 32 multiply-adds from the tiles.

for (int bk = 0; bk < K; bk += BS) {
  As[tRow * BS + tCol] = A[tRow * K + tCol];      // coalesced: tCol is the fastest index
  Bs[tRow * BS + tCol] = B[tRow * N + tCol];
  __syncthreads();
  A += BS;  B += BS * N;
  for (int d = 0; d < BS; ++d) acc += As[tRow * BS + d] * Bs[d * BS + tCol];
  __syncthreads();
}

Each element loaded from global memory is now reused 32 times, so global traffic falls by 32×. Both __syncthreads() calls are essential: remove the first and threads compute on half-loaded tiles; remove the second and fast threads overwrite a tile slower threads are still reading. (compute-sanitizer --tool racecheck catches the second bug.)

Bottleneck now: shared memory. The inner loop does 2 shared-memory loads for every FMA. Shared memory is fast, but not that fast: the load/store units saturate long before the FP32 units do. Nsight Compute reports this as high MIO throttle stalls (memory input/output queue full).

Kernel 4: 1D block tiling (more work per thread)

The fix for "too many loads per FMA" is to make each thread compute several outputs, so each loaded value is used more than once. In kernel 4, each thread computes a column of TM = 8 outputs. For each step d, it loads one value of B into a register and uses it 8 times.

for (int d = 0; d < BK; ++d) {
  const float b = Bs[d * BN + tCol];                 // one shared-memory load...
  for (int r = 0; r < TM; ++r)
    acc[r] += As[(tRow * TM + r) * BK + d] * b;      // ...used TM times
}

Shared loads per FMA fall from 2 to (TM + 1) / TM ≈ 1.1. The block tile is 64×64 with BK = 8, and acc[8] lives in registers. Speed roughly triples.

Kernel 5: 2D block tiling (register outer product)

Go further: each thread computes an 8×8 tile of outputs. For each step d it loads 8 values of A and 8 of B into registers and computes their outer product: 64 FMAs from 16 loads.

for (int d = 0; d < BK; ++d) {
  for (int i = 0; i < TM; ++i) regM[i] = As[(tRow * TM + i) * BK + d];
  for (int i = 0; i < TN; ++i) regN[i] = Bs[d * BN + tCol * TN + i];
  for (int m = 0; m < TM; ++m)
    for (int n = 0; n < TN; ++n) acc[m * TN + n] += regM[m] * regN[n];
}

Shared loads per FMA: (8 + 8) / 64 = 0.25, an 8× improvement over kernel 3. A 128×128 block tile is computed by 256 threads. The cost: 64 accumulators + 16 operands + indices ≈ 128 registers per thread, and 25% occupancy. Performance roughly doubles again, to around two-thirds of cuBLAS.

Key idea

Every level of the memory hierarchy needs its own reuse. Tiling in shared memory reduces global-memory traffic; tiling in registers reduces shared-memory traffic. Fast GEMMs are nested tilings: grid → block tile (shared memory) → warp tile → thread tile (registers) → tensor-core fragment.

Kernel 6: vectorised memory access

Two changes:

  1. 128-bit loads and stores. Load A and B from global memory as float4, and write C as float4. That's a quarter of the load instructions.
  2. Transpose the A tile in shared memory. Kernel 5 reads As[(tRow*TM + i)*BK + d], stepping by BK between consecutive i. Storing A transposed (As[d*BM + row]) makes the 8 values a thread needs contiguous, so the compiler can fetch them with wide 128-bit shared-memory loads.
float4 a4 = reinterpret_cast<const float4*>(&A[innerRowA * K + innerColA * 4])[0];
As[(innerColA * 4 + 0) * BM + innerRowA] = a4.x;     // store transposed
As[(innerColA * 4 + 1) * BM + innerRowA] = a4.y;
As[(innerColA * 4 + 2) * BM + innerRowA] = a4.z;
As[(innerColA * 4 + 3) * BM + innerRowA] = a4.w;
reinterpret_cast<float4*>(&Bs[innerRowB * BN + innerColB * 4])[0] =
    reinterpret_cast<const float4*>(&B[innerRowB * N + innerColB * 4])[0];

reinterpret_cast to float4 requires 16-byte alignment. cudaMalloc returns 256-byte-aligned pointers and our dimensions are multiples of 4, so every access is aligned. With arbitrary shapes you need a scalar fallback path, which is part of why production libraries are large.

What cuBLAS does beyond kernel 6

  • Warp tiling: an explicit level between block and thread tiles, so each warp works on a sub-tile that fits its registers and reads shared memory without bank conflicts.
  • Double buffering / multi-stage pipelines: load the next K-tile while computing on the current one, so memory latency is hidden behind math (section 7).
  • Autotuning: dozens of tile-size configurations; the library picks per shape and GPU.
  • Tensor cores whenever precision allows (TF32 is the default for FP32 matmuls in many frameworks unless you disable it).
  • Special handling of edge tiles, split-K for skinny matrices, and stream-K scheduling against wave quantization (15a).

6. Shared-memory bank conflicts

Shared memory is divided into 32 banks, each 4 bytes wide; consecutive 4-byte words sit in consecutive banks. Each bank serves one address per cycle. When threads of a warp access different addresses in the same bank, the accesses are serialised: an n-way bank conflict takes n times as long. Accessing the same address is a broadcast and is free.

bank(address) = (address in bytes ÷ 4) mod 32
Worked example

A 32×32 float tile tile[32][32], and each thread t of a warp reads tile[t][0] (a column).

word index of tile[t][0] = 32 × t → bank = (32 × t) mod 32 = 0 for every t → 32-way conflict: 32 cycles instead of 1

Fix: padding. Declare tile[32][33]. Now the word index is 33 × t, and 33t mod 32 = t, so every thread hits a different bank. One wasted column eliminates the conflict. This is the standard trick for matrix transposes.

Modern libraries use swizzling instead of padding: they XOR the column index with part of the row index when storing, so both row and column accesses are conflict-free with no wasted memory. CuTe (inside CUTLASS) and Triton handle swizzled layouts automatically. Nsight Compute's "Shared Memory" table reports bank conflicts per kernel, so measure rather than guess.

7. Tensor cores from CUDA

FP32 CUDA cores deliver a small fraction of a modern GPU's FLOPs (15a). Real AI kernels use tensor cores. There are several levels of access, from easiest to most powerful.

Level 1: the WMMA API (Volta and later)

WMMA ("warp matrix multiply-accumulate") exposes tensor cores through fragments: opaque register tiles owned collectively by a warp.

code/16a-cuda-kernels/hgemm_wmma.cu (core)

#include <mma.h>
using namespace nvcuda;

wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::row_major> a;
wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::row_major> b;
wmma::fragment<wmma::accumulator, 16, 16, 16, float> acc;
wmma::fill_fragment(acc, 0.f);

for (int k = 0; k < K; k += 16) {
  wmma::load_matrix_sync(a, A + row * K + k, K);   // whole warp loads a 16x16 tile
  wmma::load_matrix_sync(b, B + k * N + col, N);
  wmma::mma_sync(acc, a, b, acc);                  // one tensor-core operation
}
wmma::store_matrix_sync(C + row * N + col, acc, N, wmma::mem_row_major);

Each warp computes one 16×16 output tile with FP16 inputs and FP32 accumulation. This simple version loads fragments directly from global memory with no shared-memory staging, so it reaches only a fraction of cuBLAS. Even so, it typically beats the best FP32 kernel from section 5, because tensor cores are so much faster. Run ./hgemm_wmma 4096 to see both numbers.

Level 2: mma.sync, ldmatrix and cp.async (Ampere)

Serious Ampere kernels use PTX instructions directly:

  • mma.sync.aligned.m16n8k16: the underlying tensor-core instruction, with known register layouts.
  • ldmatrix: loads fragments from shared memory in exactly the layout mma needs.
  • cp.async: copies from global to shared memory without passing through registers, asynchronously. That enables multi-stage software pipelines:

With 3–4 stages in flight, memory latency is fully hidden behind math.

Level 3: Hopper's TMA, wgmma and warp specialisation

On H100, the fastest kernels are structured very differently:

  • TMA (tensor memory accelerator): one thread issues a bulk copy of a whole multi-dimensional tile from global to shared memory; the hardware computes addresses. Arrival is tracked with mbarriers (asynchronous barriers).
  • wgmma: a warpgroup (4 warps, 128 threads) issues one large asynchronous MMA that reads its operands directly from shared memory.
  • Warp specialisation: some warps act as producers (issuing TMA loads) and others as consumers (issuing wgmma), coordinating through barriers in a circular buffer of shared-memory stages. FlashAttention-3 and DeepGEMM are built this way.
  • Thread block clusters let neighbouring blocks share tiles via distributed shared memory, and multicast TMA loads a tile once into several SMs.

Level 4: Blackwell's tcgen05 and tensor memory

Blackwell moves MMA accumulators out of registers into tensor memory (TMEM), a dedicated per-SM store, and lets a pair of SMs cooperate on one MMA (cta_group::2). It adds block-scaled FP8/FP6/FP4 formats in hardware. Kernels written for Hopper need restructuring to use these; this is why each GPU generation has a lag before software reaches its peak.

8. Warp-level programming: reductions and softmax

Many AI operations reduce along a dimension: sums for normalisation, max and sum for softmax, norms for gradient clipping. They are memory-bound, so the goal is to read each byte once at full bandwidth.

Warp shuffles

Threads in a warp can read each other's registers directly with shuffle instructions, without shared memory or synchronisation:

__inline__ __device__ float warp_sum(float v) {
  for (int offset = 16; offset > 0; offset >>= 1)
    v += __shfl_down_sync(0xffffffff, v, offset);   // add the value from lane (id + offset)
  return v;                                         // lane 0 now holds the warp's total
}

reduction.cu compares three strategies for summing 64 million floats:

  1. One atomicAdd per element: every thread updates the same address; the hardware serialises them. Catastrophically slow.
  2. Shared-memory tree per block, one atomic per block: fast, but many blocks and synchronisations.
  3. Grid-stride with float4 loads, warp shuffles, one atomic per warp: each thread first sums many elements in registers, then the warp combines them. This approaches peak memory bandwidth.

Online softmax: one pass instead of three

A textbook softmax reads each row three times: find the max, sum the exponentials, normalise. The online softmax trick (Milakov and Gimelshein, 2018) computes the max and the sum together in one pass, rescaling the running sum whenever a new maximum appears:

for each element v: m_new = max(m, v) s = s · exp(m − m_new) + exp(v − m_new) m = m_new

Two partial results (m₁, s₁) and (m₂, s₂) combine the same way, so the 32 lanes of a warp can each process a strided part of the row and then merge with shuffles:

for (int off = 16; off > 0; off >>= 1) {
  float m_o = __shfl_xor_sync(0xffffffff, m, off);
  float s_o = __shfl_xor_sync(0xffffffff, s, off);
  float m_new = fmaxf(m, m_o);
  s = s * expf(m - m_new) + s_o * expf(m_o - m_new);
  m = m_new;
}

This is exactly the insight inside FlashAttention (Chapter 16 and 16b): softmax can be computed block by block without ever holding the whole row.

softmax.cu compares a naive thread-per-row kernel (uncoalesced, and only rows threads in total) with the warp-per-row online kernel. The difference on an 8192×4096 matrix is typically more than an order of magnitude.

9. Streams, concurrency and CUDA graphs

A stream is a queue of GPU work that runs in order. Work in different streams may overlap. The default stream is used when you don't specify one.

Uses of multiple streams:

  • Overlap copies with compute: copy batch i+1 to the GPU (with pinned memory and cudaMemcpyAsync) while computing batch i.
  • Overlap communication with compute: NCCL collectives run on their own streams; distributed training overlaps gradient all-reduce with the backward pass (Deep Dive 17b).
  • Run independent small kernels concurrently so they share the GPU.

Launch overhead and CUDA graphs

Each kernel launch costs a few microseconds of CPU and driver time. For a big matmul that's negligible. For LLM decode it is not: one decode step of a Transformer is hundreds of small kernels, each running for only a few microseconds at small batch sizes. The CPU can't launch them fast enough, and the GPU idles between them.

A CUDA graph records a sequence of launches once and replays the whole sequence with a single call:

cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
for (int i = 0; i < 2000; ++i) tiny<<<1, 32, 0, stream>>>(d);   // recorded, not run
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, 0);
cudaGraphLaunch(exec, stream);                                    // replays all 2,000

./cuda_graphs measures the difference on your GPU. Serving engines such as vLLM and SGLang capture the decode step as a CUDA graph for each common batch size; in PyTorch, torch.compile(mode="reduce-overhead") and torch.cuda.CUDAGraph do the same. The constraint: graphs replay fixed shapes and fixed memory addresses, which is why engines keep static buffers and pad batches to a set of captured sizes.

10. Calling your kernel from PyTorch

The quickest route is torch.utils.cpp_extension.load_inline, which compiles CUDA source at runtime and exposes it as a Python function.

code/16a-cuda-kernels/fused_bias_gelu.py (core)

cuda_src = r"""
#include <torch/extension.h>
#include <ATen/cuda/CUDAContext.h>

__global__ void bias_gelu_kernel(const float* __restrict__ x, const float* __restrict__ bias,
                                 float* __restrict__ y, long n, int cols) {
  long i = (long)blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) {
    float v = x[i] + bias[i % cols];
    y[i] = 0.5f * v * (1.f + tanhf(0.7978845608f * (v + 0.044715f * v * v * v)));
  }
}

torch::Tensor bias_gelu(torch::Tensor x, torch::Tensor bias) {
  auto y = torch::empty_like(x);
  long n = x.numel();
  auto stream = at::cuda::getCurrentCUDAStream();     // run on PyTorch's current stream
  bias_gelu_kernel<<<(n + 255) / 256, 256, 0, stream>>>(
      x.data_ptr<float>(), bias.data_ptr<float>(), y.data_ptr<float>(), n, x.size(-1));
  return y;
}
"""
ext = load_inline(name="bias_gelu_ext", cpp_sources="torch::Tensor bias_gelu(torch::Tensor x, torch::Tensor bias);",
                  cuda_sources=cuda_src, functions=["bias_gelu"], extra_cuda_cflags=["-O3"])
y = ext.bias_gelu(x, b)

The full script validates inputs with TORCH_CHECK, compares against PyTorch, and benchmarks three versions: eager PyTorch (an add kernel then a GELU kernel, so two round trips to memory), torch.compile (which generates a fused Triton kernel automatically), and the custom kernel. Expect the custom kernel and torch.compile to be similar and both faster than eager. That result is itself a lesson: try torch.compile before writing CUDA.

For production, register kernels as proper PyTorch operators with torch.library (so they work with torch.compile, autograd and export), write a backward kernel or an autograd formula, and build them ahead of time with setup.py / CUDAExtension rather than at runtime.

GPU Speed of Light What % of peak compute and peak memory bandwidth did the kernel reach? The higher one is your limiter.
Memory Workload Analysis Bytes moved at each level (L1, L2, DRAM), hit rates, shared-memory bank conflicts
Occupancy Theoretical vs achieved occupancy, and which resource limits it
Warp State Statistics Why warps were stalled (see below)
Source Counters Which source lines (with -lineinfo) cause the stalls

The most common warp stall reasons:

Stall Meaning Typical fix
Long scoreboard Waiting for global/local memory More reuse (tiling), more parallelism, prefetching, fix spills
MIO throttle / short scoreboard Shared-memory or special-function queue saturated Register tiling, vectorised shared loads, fewer bank conflicts
Barrier Waiting at __syncthreads() Balance work, fewer barriers, double buffering
Math pipe throttle Arithmetic units busy Good: you're compute-bound; use tensor cores or lower precision
Not selected / selected Warps ready but only one issues per cycle Good sign of a saturated scheduler

A performance checklist

  1. Is the kernel memory-bound or compute-bound? (Roofline, 15a.)
  2. Are global accesses coalesced and vectorised?
  3. Is every level of the hierarchy reusing data (shared-memory tiles, register tiles)?
  4. Any register spills? Any bank conflicts?
  5. Is there enough parallelism (blocks per SM, waves) for the problem size?
  6. Is the computation on tensor cores in the lowest acceptable precision?
  7. Can this kernel be fused with its neighbours to skip a round trip to memory?
  8. Is launch overhead significant (many tiny kernels)? Use CUDA graphs.

Exercises

A kernel is launched with <<<(n + 127) / 128, 128>>> for n = 1,000,000. How many threads run, and how many do nothing?

Show answer

7,813 blocks × 128 = 1,000,064 threads; 64 fail the i < n guard and do nothing.

In kernel 1, a warp's 32 threads read A[row * K + k] with row varying across the warp. With K = 4096 and FP32, how far apart are consecutive threads' addresses, and roughly how many 32-byte sectors does one warp-wide load touch?

Show answer

4,096 × 4 bytes = 16 KB apart; every thread hits a different sector, so 32 sectors (1,024 bytes fetched to use 128 bytes).

Kernel 3 uses 32×32 tiles. By what factor does it reduce global-memory loads compared with kernel 2, ignoring caches? What does the inner loop's ratio of shared-memory loads to FMAs become?

Show answer

Each loaded element is reused by 32 threads, so global loads fall ~32×. The inner loop still does 2 shared loads per FMA, which becomes the new bottleneck.

In kernel 5 with TM = TN = 8, how many shared-memory loads and FMAs happen per thread per step d? What happens to the ratio with TM = TN = 16, and why might that be slower anyway?

Show answer

16 loads, 64 FMAs (ratio 0.25). With 16×16: 32 loads, 256 FMAs (0.125). But 256 accumulators exceed the 255-register limit, causing spills to local memory and a large slowdown, and occupancy would collapse.

A block reads a column of __shared__ float t[64][64]: thread i reads t[i][5] for i in 0..31. What is the bank conflict degree? How would you fix it?

Show answer

Word index = 64i + 5 → bank (64i + 5) mod 32 = 5 for all i: a 32-way conflict. Pad to t[64][65]: bank (65i + 5) mod 32 = (i + 5) mod 32, all distinct. Or use a swizzled layout.

Show that two online-softmax partial states (m₁, s₁) and (m₂, s₂) combine into (m, s) = (max(m₁, m₂), s₁·e^(m₁−m) + s₂·e^(m₂−m)), where s is the sum of e^(x−m) over both halves.

Show answer

By definition s₁ = Σ₁ e^(x−m₁). Multiplying by e^(m₁−m) gives Σ₁ e^(x−m). Similarly for the second half. Adding them gives Σ over all elements of e^(x−m), with m the true maximum, so every exponent is ≤ 0 and nothing overflows.

A decode step at batch size 1 consists of 600 kernels averaging 4 µs of GPU time each, and each launch costs 5 µs of CPU time. Estimate the step time without and with a CUDA graph.

Show answer

Without: the CPU is the bottleneck, ~600 × 5 µs = 3.0 ms (the GPU idles ~20% of the time). With a graph: close to 600 × 4 µs = 2.4 ms plus a single launch. A 20% speed-up; larger when kernels are shorter.

Nsight Compute shows a kernel at 85% of peak DRAM bandwidth and 6% of peak compute, with "long scoreboard" as the top stall. Is it worth optimising further? What would you try?

Show answer

It is memory-bound and already near the bandwidth roofline, so tuning this kernel alone has at most ~15% left. The real gains come from moving fewer bytes: fuse it with neighbouring operations, use a lower-precision data type, or avoid materialising its output.

Build it

Project: Fuse a production hotspot

Business problem: a team serving a fine-tuned model sees that 25% of GPU time goes to "elementwise" and "reduction" kernels between the matmuls. They want a measured, safe speed-up without changing model quality.

  1. Profile. Run a real model (e.g., a 1B–8B Hugging Face model) for a forward pass under the PyTorch profiler or Nsight Systems. Rank kernels by total time and identify a chain of memory-bound ops (for example RMSNorm → multiply by weight → residual add, or bias → activation → dropout).
  2. Estimate the prize. Compute the bytes each op moves and the bytes a fused version would move. The ratio bounds your speed-up for that chain.
  3. Implement. Write a fused CUDA kernel (using this chapter's patterns: coalesced float4 loads, warp-shuffle reductions) and, for comparison, the same fusion via torch.compile.
  4. Integrate and verify. Register the kernel with torch.library, run the model with it, and check outputs match to within tolerance across a validation set.
  5. Report. End-to-end latency and throughput before and after, per-kernel Nsight Compute speed-of-light numbers, and a recommendation on whether to maintain a custom kernel or rely on the compiler.
