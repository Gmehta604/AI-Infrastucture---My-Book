Triton, Compilers and FlashAttention

Most custom GPU kernels written in the AI industry today are written in Triton, and most of the kernels your PyTorch models run are generated by a compiler that emits Triton. This deep dive teaches you to write Triton kernels, explains what torch.compile does between your Python and the GPU, and builds FlashAttention (the most consequential kernel of the last five years) from its core idea up.

1. Why Triton exists

Deep Dive 16a showed how much expertise a fast CUDA kernel needs: coalescing, shared-memory tiling, bank conflicts, register tiling, async copies, tensor-core fragment layouts, pipelining. Each GPU generation changes the details. Triton (Philippe Tillet, released by OpenAI in 2021) moves most of that work into a compiler.

CUDA C++ Triton
You program One thread One program instance working on a block of data (a tile)
Memory coalescing You arrange it Compiler
Shared memory allocation and tiling across warps You Compiler
Tensor-core instructions and layouts You (or CUTLASS) Compiler, from tl.dot
Software pipelining of loads You Compiler, from num_stages
Language C++ A subset of Python
Typical code size for a fast matmul Hundreds to thousands of lines ~50 lines
Peak performance ceiling Highest Close to it for most kernels; a gap for the most hardware-specific ones

Where Triton is used in 2026:

  • PyTorch's compiler (TorchInductor) generates Triton for GPU code. If you use torch.compile, you already run Triton.
  • Serving engines (vLLM, SGLang) implement many kernels in Triton: fused MoE, attention variants, quantization.
  • Training kernel libraries such as Liger Kernel (LinkedIn) and Unsloth provide fused RMSNorm, RoPE, SwiGLU and cross-entropy kernels in Triton, reporting large memory savings and throughput gains for LLM training.
  • Hardware portability: Triton targets NVIDIA and AMD GPUs, and backends exist for other accelerators, so a kernel written once can run on more than one vendor's hardware.
  • Gluon (2025), a lower-level Triton dialect, exposes layouts and warp specialisation explicitly for engineers who need more control on Hopper and Blackwell.

2. The programming model

A Triton kernel is a Python function decorated with @triton.jit. You launch a grid of program instances; each one processes a block of data using vector operations on whole tiles.

The essential building blocks:

Construct Meaning
tl.program_id(axis) This program's index in the grid (like blockIdx)
tl.arange(0, BLOCK) A vector of indices [0, 1, …, BLOCK-1]; BLOCK must be a power of two
ptr + offsets A block of pointers; pointer arithmetic works on whole tiles
tl.load(ptrs, mask=…, other=…) Load a tile; masked-out lanes get other
tl.store(ptrs, values, mask=…) Store a tile
tl.dot(a, b, acc) Tile matrix multiply, mapped to tensor cores
tl.sum / tl.max(x, axis) Reductions across a tile
x[:, None], x[None, :] Broadcasting to build 2D tiles from 1D index vectors
tl.constexpr A compile-time constant; the kernel is specialised (and cached) per value
num_warps, num_stages Launch options: threads per program, and pipelining depth for loops with loads

Your first kernel

code/16b-triton-flashattention/01_vector_add.py

import triton
import triton.language as tl

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(axis=0)                  # which block this program handles
    offsets = pid * BLOCK + tl.arange(0, BLOCK)  # a vector of BLOCK indices
    mask = offsets < n                           # guard the ragged last block
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)

def add(x, y, BLOCK=1024):
    out = torch.empty_like(x)
    grid = (triton.cdiv(x.numel(), BLOCK),)
    add_kernel[grid](x, y, out, x.numel(), BLOCK=BLOCK)
    return out

Compare with vector_add.cu in 16a: the logic is the same, but the unit of thought is a block, not a thread. PyTorch tensors passed to a kernel become pointers to their first element.

What the compiler does

The interesting work happens at the TritonGPU level: choosing a layout for each tile (which thread holds which elements), inserting shared-memory buffers with swizzled layouts to avoid bank conflicts, converting tl.dot into mma/wgmma instructions, and pipelining loads across loop iterations using cp.async or TMA. Each compiled variant is cached on disk (~/.triton/cache), so only the first call pays compilation time.

You can inspect every stage: kernel[grid](...) returns a compiled object whose .asm dictionary holds "ttir", "ttgir", "llir", "ptx" and "cubin". Reading the TTGIR is how experts check what layout and pipelining the compiler chose.

Debugging on a laptop

Set TRITON_INTERPRET=1 and Triton runs kernels in NumPy on the CPU. It is slow, but you can use print() and a debugger inside kernels, and you don't need a GPU. All the Triton scripts in this chapter's code folder pass their correctness checks in this mode. The workflow professionals use: develop and test correctness in the interpreter or on a small GPU, then tune on the target GPU.

Pitfall

tl.arange sizes and most tile dimensions must be powers of two. For a row of 781 elements you use a block of 1,024 and a mask. Forgetting the mask on a load reads out of bounds; forgetting it on a store corrupts memory. The interpreter and compute-sanitizer (16a) both catch these.

3. Fusing memory-bound operations

Most of the time lost outside matmuls goes to chains of memory-bound operations (15a). Fusing them into one kernel is Triton's most common use.

Fused softmax

Each program handles one row. It loads the row once into registers, computes max, exp, sum and divide, and writes once.

code/16b-triton-flashattention/02_fused_softmax.py (kernel)

@triton.jit
def softmax_kernel(out_ptr, in_ptr, in_stride, out_stride, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(in_ptr + row * in_stride + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)
    num = tl.exp(x)
    y = num / tl.sum(num, axis=0)
    tl.store(out_ptr + row * out_stride + cols, y, mask=mask)

Using -inf as the masked value matters: padding lanes then contribute nothing to the max and exp(-inf) = 0 to the sum.

A hand-written PyTorch softmax (x.max, subtract, exp, sum, divide) launches five kernels and passes over the matrix about eight times. The fused kernel passes over it twice (one read, one write), so for large matrices it approaches the bandwidth limit and runs several times faster. torch.softmax is itself a well-optimised fused kernel; the script benchmarks all three so you can see where each lands.

The limit of this design: a whole row must fit in one program's registers. For rows beyond a few tens of thousands of elements, loop over the row in chunks, using the online softmax from 16a.

Fused RMSNorm with residual add

In a Llama-style block, the residual add and the next RMSNorm are adjacent: h = x + residual; y = rmsnorm(h) * weight. Eager PyTorch runs them as around six kernels. The fused kernel reads x and residual once, writes h (needed later for the next residual) and y, and does all the math in FP32 registers regardless of input precision.

code/16b-triton-flashattention/03_rmsnorm.py (core)

acc = tl.zeros([BLOCK], dtype=tl.float32)
for start in range(0, n_cols, BLOCK):          # rows longer than BLOCK are looped over
    cols = start + tl.arange(0, BLOCK)
    mask = cols < n_cols
    h = tl.load(x_row + cols, mask=mask, other=0.0).to(tl.float32)
    if HAS_RES:                                 # constexpr: compiled away when False
        h += tl.load(res_ptr + row * stride + cols, mask=mask, other=0.0).to(tl.float32)
        tl.store(h_ptr + row * stride + cols, h, mask=mask)
    acc += h * h
rstd = 1.0 / tl.sqrt(tl.sum(acc, axis=0) / n_cols + eps)

Note two production habits here: accumulate in FP32 even for BF16 inputs, and use constexpr flags (HAS_RES) so one source file compiles into specialised variants without runtime branches.

For training you also need a backward kernel. RMSNorm's backward needs rstd per row, so forward kernels usually save it (a tiny tensor) rather than recompute it. Liger Kernel's and Unsloth's source code are good references for complete forward and backward implementations.

4. A tensor-core matmul in Triton

code/16b-triton-flashattention/04_matmul.py (core)

@triton.autotune(configs=CONFIGS, key=["M", "N", "K"])
@triton.jit
def matmul_kernel(a_ptr, b_ptr, c_ptr, M, N, K, stride_am, stride_ak, stride_bk, stride_bn,
                  stride_cm, stride_cn, ACTIVATION: tl.constexpr,
                  BM: tl.constexpr, BN: tl.constexpr, BK: tl.constexpr, GROUP_M: tl.constexpr):
    pid_m, pid_n = grouped_ordering(...)          # see below
    offs_m = (pid_m * BM + tl.arange(0, BM)) % M
    offs_n = (pid_n * BN + tl.arange(0, BN)) % N
    offs_k = tl.arange(0, BK)
    a_ptrs = a_ptr + offs_m[:, None] * stride_am + offs_k[None, :] * stride_ak   # (BM, BK) tile
    b_ptrs = b_ptr + offs_k[:, None] * stride_bk + offs_n[None, :] * stride_bn   # (BK, BN) tile

    acc = tl.zeros((BM, BN), dtype=tl.float32)
    for k in range(0, tl.cdiv(K, BK)):
        a = tl.load(a_ptrs, mask=offs_k[None, :] < K - k * BK, other=0.0)
        b = tl.load(b_ptrs, mask=offs_k[:, None] < K - k * BK, other=0.0)
        acc = tl.dot(a, b, acc)                    # tensor cores
        a_ptrs += BK * stride_ak
        b_ptrs += BK * stride_bk

    if ACTIVATION == "gelu":                       # fused epilogue, in registers
        acc = gelu_tanh(acc)
    tl.store(c_ptrs, acc.to(c_ptr.dtype.element_ty), mask=...)

Compare with kernels 3–7 of 16a: the block tile, the K loop and the accumulator are all there, but shared-memory staging, register tiling, vectorisation, bank-conflict avoidance, tensor-core fragments and multi-stage pipelining are all generated from tl.load and tl.dot plus the num_stages setting.

Grouped ordering for L2 reuse

If programs are numbered row by row across the output, consecutive programs each need a different column block of B, and B gets streamed from HBM repeatedly. Grouped ordering launches programs in groups of GROUP_M rows so that programs running at the same time share both rows of A and columns of B, which then hit in L2.

Nine output tiles from 6 input blocks instead of 10: fewer HBM reads for the same work. The effect is typically a few percent to over 10% for large matmuls.

Autotuning

@triton.autotune benchmarks each configuration (tile sizes, num_warps, num_stages) the first time the kernel sees a new value of the key arguments, and caches the winner. Good configurations depend on the GPU and on the shape: skinny decode matmuls want small BM; big prefill matmuls want large tiles and deep pipelines. Autotuning at startup is slow for many shapes, so production systems often pre-tune and ship config files (vLLM does this for its fused-MoE kernels, per GPU type).

Epilogue fusion

The activation (GELU here) is applied to the accumulator while it is still in registers, before the single store. Unfused, F.gelu(a @ b) writes the matmul output to HBM and reads it back. For large matmuls the saving is small relative to the matmul, but for the smaller matmuls of inference, and for epilogues like "dequantize + bias + activation + quantize", it matters. cuBLASLt and CUTLASS offer the same idea through epilogue APIs.

On recent NVIDIA GPUs, a well-tuned Triton FP16/BF16 matmul typically reaches a large fraction of cuBLAS performance for common shapes. Run the script on your GPU to see the numbers, and look at matmul_kernel.best_config to see what the autotuner chose.

5. How torch.compile works

torch.compile(model) turns a PyTorch program into optimised kernels. It has three stages.

Stage 1: TorchDynamo (graph capture)

Dynamo hooks into CPython's frame evaluation. It symbolically executes your function's bytecode, records tensor operations into an FX graph, and emits guards: conditions such as "x is a CUDA float16 tensor of shape (8, 512, 1024)" under which the captured graph stays valid. On later calls, if the guards pass, the compiled code runs directly.

A graph break happens when Dynamo meets something it can't put in a graph: reading a tensor value into Python (.item(), .tolist(), if tensor > 0:), printing, calling unsupported libraries, some data-dependent control flow. Dynamo then compiles the graph up to that point, runs the unsupported code in normal Python, and starts a new graph after it. Each break prevents fusion across it and adds overhead.

code/16b-triton-flashattention/07_torch_compile.py (graph breaks)

def leaky_step(x):
    scale = x.abs().max().item()     # value leaves the GPU -> graph break
    print("scale", scale)            # side effect -> graph break
    if scale > 3:
        x = x / scale
    return F.gelu(x) * 2

def fixed_step(x):                   # same maths, pure tensor ops: one graph
    scale = x.abs().amax()
    x = torch.where(scale > 3, x / scale, x)
    return F.gelu(x) * 2

torch._dynamo.explain(leaky_step)(x)   # -> 2 graphs, 1 graph break (".item() call")
torch._dynamo.explain(fixed_step)(x)   # -> 1 graph, 0 graph breaks

(That's the actual output when the script ran: the print gets folded into the break caused by .item().)

Recompilation: if a guard fails, for example a new input shape, Dynamo compiles again. With dynamic=True (or automatically after it sees a shape change), it generates kernels with symbolic shapes that work for a range of sizes. Unexpected recompiles are a common cause of slow "compiled" code; TORCH_LOGS="recompiles" shows them.

Stage 2: AOTAutograd

For training, AOTAutograd traces the backward pass ahead of time, giving the compiler a joint forward-backward graph. It decomposes high-level ops into a smaller set of primitives and decides which intermediate values to save for backward and which to recompute. Recomputing cheap elementwise results in the backward kernel is often faster than saving them to memory, a trade-off it makes automatically (a "min-cut" partitioning).

Stage 3: TorchInductor

Inductor lowers the graph to its own loop-level IR, then:

  • Fuses pointwise and reduction operations into as few kernels as possible (for example, all of RMSNorm into one kernel, or bias + SiLU + multiply into one).
  • Leaves matmuls and convolutions to cuBLAS/cuDNN by default, or generates Triton matmul templates with fused epilogues under mode="max-autotune".
  • Plans memory reuse between buffers.
  • Emits Triton code for GPUs and C++/OpenMP for CPUs, plus a Python wrapper that launches kernels in order.

Modes and settings

Setting What it does When
torch.compile(m) Default: fusion, cuBLAS for matmuls Start here
mode="reduce-overhead" Adds CUDA graphs (16a) to remove launch overhead Small batches, inference, decode
mode="max-autotune" Autotunes Triton matmul/conv templates and uses CUDA graphs; slow to compile Long-running jobs where every % matters

dynamic=True Symbolic shapes from the start Variable sequence lengths

When the chapter's script ran on a CPU, the compiled Transformer block took about 40 seconds to compile and ran about 15% faster than eager. On GPUs, where launch overhead and memory traffic dominate more, speed-ups of 1.3–2× for training and more for small-batch inference are common, but always measure.

In industry

Most teams now write models in plain PyTorch and rely on torch.compile for fusion, then write custom Triton or CUDA kernels only for the handful of hotspots the compiler can't handle well: attention variants, MoE routing, quantized matmuls, and memory-saving fusions like chunked cross-entropy. Knowing what the compiler does well is what tells you where hand-written kernels pay off.

6. FlashAttention, from first principles

The problem

Standard attention for one head computes:

S = Q·Kᵀ / √d (T × T) P = softmax(S) (T × T) O = P·V (T × d)

Written as three separate operations, S and P are written to HBM and read back. For T = 32K tokens, S and P for a single head are 1 billion entries each. With 32 heads in BF16 that is about 137 GB per layer for S and P together: far beyond any GPU. Even at moderate lengths, attention becomes memory-bound on reading and writing these matrices, not on its FLOPs.

python 05_flash_attention_numpy.py prints this table for a 32-head, d = 128 layer:

Sequence length S and P stored (all heads)
1,024 0.13 GB
4,096 2.1 GB
16,384 34 GB
131,072 2,199 GB

The idea

FlashAttention (Tri Dao and colleagues, 2022) combines two tricks:

  1. Tiling. Split Q into blocks of rows and K, V into blocks of columns. Load a Q block into on-chip memory, then stream K and V blocks past it.
  2. Online softmax (16a). Softmax needs a whole row's max and sum, but those can be maintained incrementally, rescaling earlier partial results when a new maximum appears. The same rescaling applies to the partial output acc = Σ p·V.

The output is computed exactly, not approximately, and the T × T matrices never exist in HBM.

code/16b-triton-flashattention/05_flash_attention_numpy.py (core)

for i in range(0, T, Br):                          # a block of query rows
    q = Q[i:i + Br]
    m = np.full(len(q), -np.inf); l = np.zeros(len(q)); acc = np.zeros((len(q), d))
    for j in range(0, T, Bc):                      # stream key/value blocks past it
        s = q @ K[j:j + Bc].T * scale              # a Br x Bc tile of scores
        m_new = np.maximum(m, s.max(axis=1))
        p = np.exp(s - m_new[:, None])
        alpha = np.exp(m - m_new)                  # rescale what we had so far
        l = l * alpha + p.sum(axis=1)
        acc = acc * alpha[:, None] + p @ V[j:j + Bc]
        m = m_new
    O[i:i + Br] = acc / l[:, None]

Run it: the tiled result matches standard attention to about 10⁻¹⁵, for both causal and non-causal attention, on a sequence length (300) that isn't a multiple of the block size.

IO complexity

For sequence length N, head dimension d and on-chip memory of size M, the paper shows:

Standard attention HBM accesses: Θ(N·d + N²) FlashAttention HBM accesses: Θ(N²·d² / M)

With typical d (64–128) and M (around 100–200 KB of SRAM per SM), d²/M is well below 1, so FlashAttention reads and writes several times less. More importantly, its memory is O(N) instead of O(N²), which is what made long-context training practical.

The backward pass

Training needs gradients with respect to Q, K and V, which normally uses the saved P matrix. FlashAttention doesn't store P. Instead it saves only the per-row logsumexp (m + log l, one number per row) and recomputes each P tile during the backward pass from Q, K and that statistic. Recomputation costs extra FLOPs, but FLOPs are cheap and HBM traffic is not, so the backward pass is still faster than the standard one. This "recompute instead of store" pattern appears throughout AI infrastructure (activation checkpointing, AOTAutograd's partitioning).

A FlashAttention kernel in Triton

code/16b-triton-flashattention/06_flash_attention_triton.py (core)

@triton.jit
def attn_fwd(Q, K, V, O, stride_bh, stride_t, T, sm_scale,
             D: tl.constexpr, BM: tl.constexpr, BN: tl.constexpr, CAUSAL: tl.constexpr):
    start_m = tl.program_id(0)                     # block of query rows
    bh = tl.program_id(1)                          # (batch, head)
    offs_m = start_m * BM + tl.arange(0, BM)
    offs_n = tl.arange(0, BN)
    offs_d = tl.arange(0, D)
    base = bh * stride_bh
    q = tl.load(Q + base + offs_m[:, None] * stride_t + offs_d[None, :], mask=offs_m[:, None] < T, other=0.0)

    m_i = tl.full([BM], float("-inf"), dtype=tl.float32)
    l_i = tl.zeros([BM], dtype=tl.float32)
    acc = tl.zeros([BM, D], dtype=tl.float32)
    qk_scale = sm_scale * 1.4426950408889634       # log2(e): lets us use the cheaper exp2

    hi = T
    if CAUSAL:
        hi = tl.minimum((start_m + 1) * BM, T)     # skip key blocks entirely above the diagonal
    for start_n in range(0, hi, BN):
        cols = start_n + offs_n
        k = tl.load(K + base + cols[None, :] * stride_t + offs_d[:, None], mask=cols[None, :] < T, other=0.0)
        qk = tl.dot(q, k) * qk_scale
        valid = cols[None, :] < T
        if CAUSAL:
            valid = valid & (offs_m[:, None] >= cols[None, :])
        qk = tl.where(valid, qk, float("-inf"))
        m_new = tl.maximum(m_i, tl.max(qk, 1))
        p = tl.math.exp2(qk - m_new[:, None])
        alpha = tl.math.exp2(m_i - m_new)
        l_i = l_i * alpha + tl.sum(p, 1)
        acc = acc * alpha[:, None]
        v = tl.load(V + base + cols[:, None] * stride_t + offs_d[None, :], mask=cols[:, None] < T, other=0.0)
        acc = tl.dot(p.to(v.dtype), v, acc)
        m_i = m_new

    acc = acc / l_i[:, None]
    tl.store(O + base + offs_m[:, None] * stride_t + offs_d[None, :], acc.to(O.dtype.element_ty), mask=offs_m[:, None] < T)

It is the NumPy algorithm almost line for line, with two GPU-specific touches: exp2 with log₂(e) folded into the scale (the hardware's native exponential is base 2), and causal block skipping, which halves the work for causal attention by never visiting key blocks entirely in the future. The script checks it against torch.nn.functional.scaled_dot_product_attention in both modes (it passes in the CPU interpreter), then on a GPU benchmarks it against PyTorch's built-in FlashAttention and a naive implementation, and compares peak memory.

FlashAttention 1 → 4

Version Year Main ideas Result reported by the authors
FlashAttention 2022 Tiling + online softmax + recomputation in backward 2–4× faster attention; exact; linear memory
FlashAttention-2 2023 Parallelise over the sequence as well as batch and heads; fewer non-matmul FLOPs; better division of work between warps About 2× over FA1; 50–73% of theoretical peak on A100
FlashAttention-3 2024 Hopper-specific: warp specialisation (producer warps issue TMA loads, consumer warpgroups run wgmma), overlapping softmax of one block with the matmul of the next, FP8 with incoherent processing to limit quantization error Up to ~740 TFLOP/s FP16 (~75% of H100 peak), close to 1.2 PFLOP/s in FP8
FlashAttention-4 2025 Blackwell-specific: tensor memory, new pipeline, software exponential approximations to relieve the special-function units Targets B200-class GPUs; written with the CuTe DSL

Each version exists because each GPU generation changed the balance between matmul throughput, memory bandwidth and non-matmul throughput. On Hopper and Blackwell, the softmax's exponentials run on much slower units than the tensor cores, so hiding them became the main challenge.

Attention for inference: FlashDecoding and paged attention

During decode, there is one query per sequence and a very long KV cache. The FA2 parallelisation (over query blocks) has almost nothing to parallelise, so most SMs sit idle. FlashDecoding (2023) splits the KV sequence into chunks processed in parallel by different programs, each producing a partial (m, l, acc), then combines them with the same rescaling rule: online softmax again. Serving engines combine this with paged KV caches (Deep Dive 19a), where K and V live in non-contiguous blocks addressed through a block table; FlashInfer and vLLM's attention backends provide these kernels.

FlexAttention: attention variants without writing kernels

Research keeps producing attention variants: sliding windows, document masking for packed sequences, ALiBi, soft-capping, prefix-LM masks. Writing a FlashAttention kernel for each is impractical. FlexAttention (PyTorch, 2024) lets you write the variant as a small Python function; torch.compile turns it into a fused Triton FlashAttention kernel, and a block mask lets it skip fully masked tiles.

from torch.nn.attention.flex_attention import flex_attention, create_block_mask

def sliding_window_causal(b, h, q_idx, kv_idx):          # mask_mod: which positions may attend
    return (q_idx >= kv_idx) & (q_idx - kv_idx <= 1024)

def soft_cap(score, b, h, q_idx, kv_idx):                # score_mod: transform scores
    return 30.0 * torch.tanh(score / 30.0)

block_mask = create_block_mask(sliding_window_causal, B=None, H=None, Q_LEN=T, KV_LEN=T)
out = torch.compile(flex_attention)(q, k, v, score_mod=soft_cap, block_mask=block_mask)

The block mask is what makes a sliding window fast: tiles entirely outside the window are never loaded, exactly like causal block skipping in our Triton kernel.

Exercises

A softmax kernel is launched with BLOCK = triton.next_power_of_2(n_cols). For n_cols = 5,000, what is BLOCK, and what fraction of lanes are masked out?

Show answer

8,192; (8,192 − 5,000) / 8,192 ≈ 39% of lanes do no useful work. For awkward sizes it can be better to loop over the row with a smaller block.

Why does the softmax kernel load masked lanes with other=-float("inf") rather than other=0?

Show answer

With 0, padding lanes could become the row maximum (if all real values are negative) and each would add exp(0 − max) to the sum, giving wrong probabilities. With −inf they never win the max and contribute exp(−inf) = 0.

A matmul's output is a 12 × 12 grid of tiles; 36 programs run at once. How many distinct A row-blocks and B column-blocks does the first wave need with row-major ordering, and with GROUP_M = 6?

Show answer

Row-major: 36 programs cover 3 full rows of 12 tiles: 3 A blocks + 12 B blocks = 15. Grouped (6 rows): the first 36 programs cover a 6 × 6 square: 6 + 6 = 12. Fewer distinct inputs means more L2 hits.

Name two constructs that cause a graph break in torch.compile, and give a tensor-only rewrite for one of them.

.item() / .tolist(), print, Python if on a tensor value, unsupported third-party calls. Rewrite if x.sum() > 0: y = a else: y = b as y = torch.where(x.sum() > 0, a, b).

Estimate the memory needed to store S (in BF16) for one layer with 32 heads at T = 8,192. How much does FlashAttention store for the backward pass instead?

Show answer

32 × 8,192² × 2 bytes ≈ 4.3 GB (and the same again for P). FlashAttention stores only the logsumexp: 32 × 8,192 × 4 bytes ≈ 1 MB, plus the output O.

In the online-softmax loop, what happens to acc and l when a later block contains a new, larger maximum? Why is the final result still exact?

Show answer

Both are multiplied by alpha = exp(m_old − m_new) < 1, which re-expresses everything accumulated so far relative to the new maximum. Since exp(x − m_old) · exp(m_old − m_new) = exp(x − m_new), every term ends up relative to the global maximum, exactly as in standard softmax.

For causal attention with BM = BN = 64 and T = 4,096, how many (query block, key block) tile pairs does our kernel visit, compared with non-causal?

Show answer

64 query blocks. Non-causal: 64 × 64 = 4,096 pairs. Causal: query block i visits i + 1 key blocks, so 1 + 2 + … + 64 = 2,080 pairs, about 51%.

During decode with batch 1, one head, and a 128K-token KV cache, why does a FlashAttention-2 style kernel use the GPU poorly, and how does FlashDecoding fix it?

Show answer

FA2 parallelises over query blocks, batch and heads; with one query and one sequence there are very few programs, so most SMs idle. FlashDecoding splits the 128K keys into chunks handled by separate programs in parallel, then merges their partial (m, l, acc) results with the online-softmax combination rule.

Build it

Project: Stop the out-of-memory errors in long-context fine-tuning

Business problem: a team fine-tuning a Llama-3-class model (vocabulary 128,256) at 8K context runs out of memory. The profiler shows the biggest single allocation is the logits tensor: 8 sequences × 8,192 tokens × 128,256 vocab × 4 bytes (FP32) ≈ 33.6 GB, plus the same again for its gradient.

  1. Measure. Reproduce the problem with a small model and a large vocabulary; record peak memory with torch.cuda.max_memory_allocated() and tokens/second.
  2. Fuse. Write a Triton kernel (or chain of kernels) for chunked fused linear + cross-entropy: process the tokens in chunks, compute each chunk's logits, the loss and the gradient with respect to the logits in one pass, and never materialise the full logits tensor. Liger Kernel's FusedLinearCrossEntropy is a reference design once you've tried it yourself.
  3. Verify. The loss and gradients must match PyTorch's to within tolerance on a validation batch.
  4. Report. Peak memory, throughput, and the largest batch or context length that now fits, before and after. Translate it into money: fewer GPUs per job, or longer contexts on the same hardware.
