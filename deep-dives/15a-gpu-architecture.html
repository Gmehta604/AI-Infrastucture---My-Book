GPU Architecture and the Performance Model

This deep dive turns the GPU from a black box into a machine you can reason about on paper. By the end you should be able to look at any AI workload, from a training step to a single decoded token, and predict roughly how fast it can possibly run, what limits it, and what to change. That skill underlies every other infrastructure chapter.

1. Two kinds of processors

A CPU and a GPU are optimised for opposite goals.

  • A CPU minimises latency: how long one task takes. It spends its transistors on large caches, branch predictors, out-of-order execution and speculative execution, so one thread runs as fast as possible.
  • A GPU maximises throughput: how much total work finishes per second. It spends its transistors on many simple arithmetic units and huge register files, and accepts that each individual thread is slow.

The key consequence: a GPU is fast only when you give it enough independent work to keep thousands of arithmetic units busy while other work waits for memory. Almost every performance problem in AI infrastructure is a version of "not enough parallel work" or "too much time waiting on memory".

Latency hiding and Little's law

Reading from HBM takes roughly 500–800 nanoseconds on modern GPUs. At about 1.8 GHz, that is over a thousand clock cycles during which a thread waiting for data does nothing. A GPU does not try to make that wait shorter. Instead, it switches to other threads that are ready to run, so the arithmetic units stay busy. This is latency hiding.

How much work must be in flight? Little's law from queueing theory answers it:

Concurrency (bytes in flight) = Bandwidth × Latency
Worked example

To saturate an H100's 3.35 TB/s of HBM bandwidth with ~600 ns latency:

bytes in flight = 3.35 × 10¹² B/s × 600 × 10⁻⁹ s ≈ 2.0 MB per SM (132 SMs) ≈ 15 KB in flight at all times

If each thread loads 16 bytes at a time, that is about 950 outstanding loads per SM. With 2,048 threads per SM, it is achievable, but only if the kernel keeps enough threads resident and issues loads early. A kernel that runs only a few hundred threads per SM, or that waits for each load before issuing the next, cannot reach full bandwidth no matter how clever its math is.

This one calculation explains why occupancy, asynchronous copies and prefetching matter so much, and why a single small request to a GPU (batch size 1) wastes most of the chip.

2. Anatomy of an H100

We use the H100 SXM (Hopper, 2022) as our reference because it is well documented and still widely deployed. Blackwell and Rubin follow the same design with more of everything (section 9).

Inside one streaming multiprocessor (SM)

The SM is the unit that actually runs your code. Everything else exists to feed SMs with data.

Per-SM resource (H100) Amount Why it matters
Sub-partitions (processing blocks) 4 Each has its own scheduler and tensor core
Max resident threads 2,048 (64 warps) Upper bound on parallelism for latency hiding
Max resident thread blocks 32 Tiny blocks can hit this limit
32-bit registers 65,536 (256 KB) The fastest storage; shared among all resident threads
Max registers per thread 255 Heavy kernels spill to slow "local memory" beyond this
Shared memory / L1 256 KB combined; up to 228 KB shared Programmer-managed scratchpad for tiling
Tensor cores 4 Nearly all the FLOPs
FP32 CUDA cores 128 Everything that isn't a matrix multiply

Two numbers deserve memorising: 65,536 registers and 2,048 threads per SM. Divide one by the other: a kernel can use at most 32 registers per thread if it wants all 2,048 threads resident. Use more registers and fewer threads fit. That trade-off, between per-thread resources and parallelism, is at the heart of kernel design.

Deriving the peak FLOP/s yourself

Datasheet numbers are not magic; they are products of simple factors.

Peak = (number of SMs) × (FLOPs per SM per clock) × (clock rate) H100 SXM, dense BF16: 132 SMs × 4 tensor cores × 1,024 FLOPs per tensor core per clock × ~1.83 GHz = 132 × 4,096 × 1.83 × 10⁹ ≈ 989 × 10¹² FLOP/s ≈ 989 TFLOP/s

Change one factor and the peak moves: FP8 doubles FLOPs per clock (1,979 TFLOP/s); FP32 on the plain CUDA cores gives 132 × 128 lanes × 2 (fused multiply-add) × ~1.98 GHz ≈ 67 TFLOP/s. That 15× gap between tensor cores and ordinary cores is why a model whose math doesn't land on tensor cores runs at a fraction of the chip's capability.

Pitfall

"Sparse" figures on datasheets (often shown first and in bold) assume 2:4 structured sparsity, where half of every four weights are zero. Almost no LLM training or serving uses this. Divide sparse figures by two, and always compare dense numbers.

3. The execution model: threads, warps, blocks, grids

CUDA organises work in a hierarchy that maps directly onto the hardware.

Software concept Hardware home Facts to know
Thread A lane in a sub-partition Has private registers
Warp (32 threads) A warp scheduler Executes one instruction for all 32 threads at once (SIMT)
Warpgroup (4 warps, Hopper+) All 4 sub-partitions Unit that issues wgmma tensor-core instructions
Thread block (CTA) One SM Up to 1,024 threads; shares shared memory; can synchronise with __syncthreads()
Thread block cluster (Hopper+) Up to 16 SMs in a GPC Blocks can read each other's shared memory (distributed shared memory)
Grid The whole GPU All blocks of one kernel launch

SIMT and warp divergence

A warp executes a single instruction stream. If threads in a warp take different branches of an if, the warp executes both paths, masking off inactive threads each time. Code like if (threadIdx.x % 2 == 0) {...} else {...} halves throughput. Branch on values that are uniform across a warp whenever possible.

Scheduling and latency hiding in practice

Each clock, each warp scheduler picks one eligible warp (one whose next instruction has its inputs ready) and issues its instruction. If all resident warps are stalled waiting for memory, the scheduler idles, and so does its share of the SM. More resident warps give the scheduler more chances to find eligible work.

Occupancy

Occupancy = resident warps ÷ maximum warps (64 on H100). It is limited by whichever resource runs out first: threads, registers, shared memory, or block slots.

Worked example

A kernel uses blocks of 256 threads (8 warps), 64 registers per thread, and 48 KB of shared memory per block.

Registers per block = 256 × 64 = 16,384 → 65,536 / 16,384 = 4 blocks Shared memory = 228 KB / 48 KB → 4 blocks Threads = 2,048 / 256 → 8 blocks Resident blocks = min(4, 4, 8, 32) = 4 → 32 warps → occupancy 50%

To reach 100% occupancy you would need to cut registers to 32 per thread and shared memory to 28 KB per block. Whether that is worth it depends on the kernel, which is the next point.

Run python occupancy.py --threads 256 --regs 64 --smem-kb 48 in the chapter's code folder to explore this.

Key idea

High occupancy is a means, not a goal. Memory-bound kernels (elementwise ops, normalisations) need high occupancy to keep enough loads in flight. Compute-bound kernels (matmuls, FlashAttention) often run best at low occupancy with very large register tiles, because data reused from registers never touches memory at all. Modern Hopper and Blackwell GEMM kernels commonly run one or two large thread blocks per SM.

4. The memory hierarchy in depth

Level Capacity (H100) Approx. bandwidth Approx. latency Managed by
Registers 256 KB per SM (33 MB total) Highest: operands every cycle ~1 cycle Compiler
Shared memory / L1 up to 228 KB per SM (~30 MB total) ~30+ TB/s aggregate ~20–30 cycles Programmer (shared) / hardware (L1)
Distributed shared memory Across a cluster of SMs Lower than local shared memory Tens of cycles Programmer (Hopper+)
L2 cache 50 MB ~10 TB/s-class ~200–300 cycles Hardware
HBM3 80 GB 3.35 TB/s peak ~500–800 ns Programmer via global memory
Peer GPU over NVLink 80 GB each 900 GB/s total per GPU (450 each way) Microseconds NCCL / programmer
Host memory over PCIe Gen5 Hundreds of GB ~64 GB/s each way Microseconds Programmer / driver

Two things stand out. First, each level down is roughly an order of magnitude slower in bandwidth. Second, the fastest levels are tiny: all the registers and shared memory on the chip together hold about 60 MB, compared with 80 GB of HBM. Kernel design is the art of arranging computation so that each byte fetched from HBM is reused as many times as possible from registers and shared memory before it is evicted.

Coalescing: how global memory is really read

HBM is accessed in 32-byte sectors grouped into 128-byte cache lines. When the 32 threads of a warp load 32 consecutive 4-byte values, the hardware combines them into four 32-byte sectors: one efficient transaction. If the threads load addresses that are far apart (for example, walking down a column of a row-major matrix), each thread may trigger its own sector, wasting up to 8× bandwidth.

This is why tensor layout (row-major vs column-major, which dimension is contiguous) matters so much, and why a transposed tensor in PyTorch can make an operation mysteriously slow. Chapter 16a covers shared-memory bank conflicts, the equivalent problem one level up.

The L2 cache and data reuse

At 50 MB, the H100's L2 can hold, for example, the full KV cache of a small model's short conversation, or a few layers' worth of weights for a small model. Kernels that process data in L2-friendly orders (for example, "swizzling" the order in which a GEMM computes output tiles so neighbouring tiles share inputs) can cut HBM traffic noticeably. You mostly get this for free from good libraries, but it explains why the same GEMM can differ in speed between libraries.

5. Tensor cores

Tensor cores compute a small matrix multiply-accumulate, D = A × B + C, in one operation. Every generation has increased their size, their supported precisions, and how asynchronously they run.

Generation GPU New precisions Programming interface What changed for kernels
1st V100 (2017) FP16 wmma, mma Tensor cores appear
2nd T4 (2018) INT8, INT4 mma Inference precisions
3rd A100 (2020) BF16, TF32, FP64 mma.sync + cp.async Async copies from global to shared memory
4th H100 (2022) FP8 wgmma (warpgroup MMA), TMA Tensor cores read operands directly from shared memory, asynchronously; a whole warpgroup issues one large MMA
5th B200/B300 (2025) FP6, FP4, NVFP4, MXFP4/6/8 tcgen05.mma, Tensor Memory (TMEM) Accumulators live in dedicated tensor memory, not registers; pairs of SMs cooperate on one MMA
6th Rubin (2026) NVFP4 at much higher rate Evolving More FP4 throughput; HBM4

Why dimensions should be multiples of 8, 16, 64 or 128

Tensor core instructions operate on fixed tile shapes (for example, a Hopper wgmma computes a 64×N×16 tile, with N up to 256). If a matrix dimension is not a multiple of the tile size, libraries either pad (wasted work) or fall back to slower paths. Rules of thumb:

  • Keep hidden sizes, head dimensions and batch×sequence products as multiples of 64 or 128.
  • Pad vocabulary sizes to a multiple of 64 or 128 (a well-known nanoGPT trick: 50,257 → 50,304).
  • Keep BF16/FP16 tensors 16-byte aligned (multiples of 8 elements).

Tile quantization and wave quantization

A GEMM library splits the output matrix into tiles, say 128×128, and gives each SM one tile at a time. Two kinds of waste follow.

  • Tile quantization: if a dimension is 4,097, the last row of tiles is almost entirely padding. You pay for a 4,224-wide computation.
  • Wave quantization: tiles are processed in "waves" of 132 (one per SM). If there are 144 tiles, the first wave uses all 132 SMs and the second uses only 12, so the second wave takes as long as the first while leaving 120 SMs idle.
Worked example

On an H100 with 128×128 tiles:

M = N = 1,408: 11 × 11 = 121 tiles → 1 wave at 121/132 = 92% utilisation M = N = 1,536: 12 × 12 = 144 tiles → 2 waves at 144/264 = 55% utilisation

The larger matrix does 19% more work but takes about twice as long. This is why matmul throughput plotted against size looks like a saw blade, and why benchmarking at the exact shapes your model uses matters. Run python wave_quantization.py to reproduce the table.

Libraries fight this with multiple tile sizes, split-K (dividing the inner dimension across more tiles), and stream-K / persistent kernels that divide the total work evenly across SMs rather than by tiles.

6. The roofline model, properly

The roofline model (Williams, Waterman and Patterson, 2009) bounds the performance of any kernel with two numbers from the hardware and one from the kernel.

Arithmetic intensity (AI) = FLOPs performed ÷ bytes moved to/from memory Attainable FLOP/s = min( Peak FLOP/s , Bandwidth × AI ) Ridge point = Peak FLOP/s ÷ Bandwidth

Ridge points across chips

Chip Dense BF16 HBM bandwidth Ridge (BF16) Ridge (FP8) Ridge (FP4)
A100 80GB 312 TF 2.0 TB/s 156 — —
H100 SXM 989 TF 3.35 TB/s 295 591 —
H200 989 TF 4.8 TB/s 206 412 —
B200 ~2.25 PF 8 TB/s ~281 ~562 ~1,125
MI300X ~1.31 PF 5.3 TB/s ~247 ~493 —
MI355X ~2.5 PF 8 TB/s ~312 ~625 ~1,250
Rubin (vendor figures) — ~22 TB/s — — ~2,273

Notice the trend: compute grows faster than bandwidth, so ridge points rise at low precision. More and more operations become memory-bound with each generation, which is why memory bandwidth, HBM capacity, and techniques that reduce bytes (quantization, KV-cache compression, fusion) keep gaining importance. H200 is the interesting exception: the same compute as H100 with 43% more bandwidth, which makes it markedly better for memory-bound decode.

Hierarchical rooflines

The same idea applies to each memory level: a kernel may be bound by L2 bandwidth or shared-memory bandwidth rather than HBM. NVIDIA Nsight Compute shows a "speed of light" chart with the percentage of peak reached for compute and for each memory level; the highest bar is your limiter.

7. A Transformer layer on the roofline

Let's place each operation of a Llama-3-8B-style layer (d = 4,096, d_ff = 14,336) on an H100's roofline, for different numbers of tokens processed at once (T).

For a linear layer with weight d_in × d_out applied to T tokens in BF16:

FLOPs = 2 · T · d_in · d_out Bytes ≈ 2 · (d_in · d_out + T · d_in + T · d_out) (weights + input + output) AI ≈ T when T is much smaller than d_in and d_out

The arithmetic intensity of a linear layer is roughly the number of tokens processed together. Weights dominate the bytes, and each weight byte is used once per token.

Operation T = 1 (decode, batch 1) T = 256 T = 4,096 (prefill / training)
QKV projection AI ≈ 1 → memory-bound, ~3 TF AI ≈ 236 → ~790 TF AI ≈ 1,755 → compute-bound, 989 TF
MLP matmuls AI ≈ 1 AI ≈ 237–239 AI ≈ 1,790–1,910
RMSNorm AI ≈ 1 AI ≈ 1.2 AI ≈ 1.2 (always memory-bound)
Residual add AI ≈ 0.17 0.17 0.17 (always memory-bound)
Softmax AI ≈ 1.2 1.2 1.2 (always memory-bound)

Run python roofline.py --tokens 1 256 4096 to reproduce these numbers and plot them.

Three lessons fall out:

  1. Decode at batch size 1 uses about 0.3% of an H100's compute. The weights must be read for every token, and each weight is used for a single multiply-add.
  2. The batch size needed to become compute-bound is roughly the ridge point: about 300 tokens per step on an H100 in BF16. With FP8 weights (half the bytes) but FP8 compute (double the peak), the ridge doubles too, so you need about 600. This is the fundamental reason serving engines work so hard to batch requests (Chapter 19a).
  3. Normalisations, activations and residual adds are always memory-bound. They contribute few FLOPs but real time, which is why they are fused into neighbouring matmuls or into each other.
Key idea

Prefill and training are compute problems: make the matmuls efficient. Decode is a memory problem: move fewer bytes per token, and share each byte across more tokens by batching.

Attention is different

During decode, attention reads the KV cache, which is different for every sequence. Batching does not share it: 64 sequences read 64 caches. So the attention part of decode stays memory-bound at any batch size, and at long contexts the KV cache, not the weights, becomes the dominant traffic. Techniques such as GQA, MLA, KV quantization and sparse attention (Chapters 9, 11 and 19) all attack this.

8. From bytes to tokens per second and dollars

We can now estimate serving performance from the datasheet alone.

Decode step time ≈ (weight bytes + batch × KV bytes read per sequence) ÷ (achievable bandwidth) Tokens/s (total) = batch ÷ step time Cost per million tokens = (GPU $/hour × number of GPUs) ÷ (tokens/s × 3,600) × 10⁶
Worked example

Serve Llama-3-70B in BF16 on H100s with 8K-token contexts.

  1. Memory. Weights: 70 × 10⁹ × 2 bytes = 140 GB. KV cache per token: 2 × 80 layers × 8 KV heads × 128 × 2 bytes = 320 KB. A full 8K-token sequence: 2.7 GB. Two H100s (160 GB) cannot even hold the weights with room for cache, so we use four GPUs with tensor parallelism (320 GB total, ~288 GB usable).
  2. Capacity. After 140 GB of weights, ~148 GB remain: about 55 full 8K-token sequences.
  3. Speed at batch 1. Each step reads 140 GB across 4 GPUs at ~80% of 4 × 3.35 TB/s ≈ 10.7 TB/s: about 13 ms per step, so ~75 tokens/s for that one user.
  4. Speed at batch 55. Step reads 140 GB of weights + 55 sequences × ~1.35 GB of KV (half-full on average) ≈ 214 GB → ~20 ms per step → ~2,750 tokens/s total, ~50 tokens/s per user.
  5. Cost. At $2.50 per GPU-hour, 4 GPUs cost $10/hour. At batch 1: $10 ÷ (75 × 3,600) × 10⁶ ≈ $37 per million tokens. At batch 55: ≈ $1.01 per million tokens.

Same hardware, 36× cost difference, purely from utilisation. Switching to FP8 weights (70 GB) would also free memory for roughly twice the concurrent sequences and cut per-step weight traffic in half. Run python memory_planner.py --params 70 --layers 80 --kv-heads 8 --gpu H100-SXM to reproduce this, then try --weight-bytes 1 and --gpu H200.

These estimates are typically within 20–40% of what a well-tuned engine achieves. That's good enough to make purchasing and architecture decisions before you rent anything.

9. Generations and competitors

NVIDIA Hopper (H100, H200)

Key features beyond the tensor cores: TMA (a hardware unit that copies multi-dimensional tiles between global and shared memory asynchronously, freeing threads from address arithmetic), thread block clusters and distributed shared memory, and the Transformer Engine (software plus hardware for per-tensor FP8 scaling). H200 is the same GH100 die with 141 GB of faster HBM3e.

NVIDIA Blackwell (B200, B300, GB200/GB300)

  • Two reticle-sized dies in one package joined by a 10 TB/s die-to-die link, presented to software as one GPU.
  • 5th-generation tensor cores with FP4/FP6 and block-scaled "microscaling" formats (NVFP4 uses a scale per 16 values), and tensor memory (TMEM), a dedicated per-SM store for MMA accumulators that frees registers.
  • NVLink 5 at 1.8 TB/s per GPU; NVL72 racks with 72 GPUs in one NVLink domain.
  • B300 (Blackwell Ultra) raises HBM to 288 GB and FP4 throughput further, aimed squarely at reasoning-model inference.
  • A decompression engine and RAS engine (reliability monitoring) for data-center use.

NVIDIA Rubin (H2 2026)

Vendor figures: ~50 PFLOP/s of NVFP4 per GPU, 288 GB of HBM4 at ~22 TB/s, NVLink 6 at 3.6 TB/s per GPU, paired with the Arm-based Vera CPU in Vera Rubin NVL72 racks. The platform adds Rubin CPX, a GDDR7-based chip specialised for the compute-heavy prefill phase, and a Groq-derived low-latency decode accelerator (LPX). The design explicitly splits prefill and decode across different silicon, a pattern you'll meet in software in Chapter 19c.

AMD Instinct (MI300X, MI325X, MI355X, MI400 series)

AMD builds GPUs from chiplets: the MI300X has eight compute dies (XCDs) with 304 compute units, a 256 MB Infinity Cache, and 192 GB of HBM3 at 5.3 TB/s. Differences that matter for engineers:

  • AMD's wavefront is 64 threads (vs NVIDIA's 32-thread warp).
  • More HBM per GPU has made AMD attractive for serving large models on fewer GPUs.
  • Software runs on ROCm; PyTorch, vLLM and SGLang support it, and performance gaps have narrowed, but kernel availability still lags CUDA for newer techniques.
  • The MI355X (CDNA 4, 288 GB) and the MI400 series with the Helios rack-scale system (2026) move toward NVIDIA's rack-scale approach.

Google TPU

A TPU core is built around matrix multiply units (MXUs): large systolic arrays (128×128 in older generations, 256×256 in Trillium and later) where data flows through a grid of multiply-accumulate cells, each value reused as it passes. There are no warps or thread blocks; the XLA compiler schedules everything. Chips connect directly through ICI links in 2D/3D torus topologies, with optical circuit switches connecting thousands of chips into pods. The v7 Ironwood generation (2025) offers ~4.6 PFLOP/s FP8 and 192 GB of HBM per chip, in pods of up to 9,216 chips.

SRAM-centric designs (Groq, Cerebras)

Groq's LPU and Cerebras's wafer-scale engine keep model weights in on-chip SRAM spread across many chips (or one giant wafer), trading capacity for enormous bandwidth. The result is very fast single-stream decode (hundreds to thousands of tokens per second per user), useful for latency-critical applications, at the cost of needing many chips per model.

Choosing hardware for a workload

Workload What limits it Favour
Large-scale pretraining Compute, interconnect, reliability Newest generation, large NVLink domains, proven software
MoE training All-to-all communication Large scale-up domains (NVL72), fast networks
Decode-heavy serving (chat, agents) HBM bandwidth and capacity High bandwidth per dollar (H200, B300, MI3xx), FP8/FP4 support

10. Power, clocks and reality

Datasheet peaks assume maximum boost clocks. In practice:

  • GPUs have a power limit (700 W for H100 SXM; ~1,000–1,400 W for Blackwell parts). Heavy tensor-core work often hits it, and clocks drop. Sustained matmul throughput is commonly 70–80% of the datasheet peak on H100 with the best libraries.
  • Thermal throttling happens with poor cooling; watch nvidia-smi -q -d PERFORMANCE for throttle reasons.
  • Achievable HBM bandwidth is typically 85–93% of peak for a simple copy.
  • Some operators cap power (e.g., 500–600 W) to fit more GPUs in a power budget. Throughput falls less than proportionally, so performance per watt often improves.
In industry

Hyperscalers and labs track MFU (model FLOPs utilisation) for training and tokens per second per GPU or tokens per watt for serving. A dense-model training run at 40–50% MFU on H100s is considered good; MoE runs are usually lower because of communication. When you read that a lab "improved throughput by 30%", it is almost always a better kernel, less communication, or larger effective batch, not new hardware.

11. Measuring your GPU

The chapter's microbench.py measures three things on whatever device you run it on: copy bandwidth, matmul throughput across sizes and precisions, and the contrast between an elementwise add and a matmul. On an H100 you should see roughly:

Test Expect If much lower, suspect
2 GB copy ~2.8–3.1 TB/s PCIe variant (2.0 TB/s), power cap, other jobs on the GPU
BF16 matmul 8192³ ~650–800 TFLOP/s TF32/FP32 path, throttling, old library
BF16 matmul 1536³ Visibly lower than 1408³ That's wave quantization; expected
Elementwise add ~0.5 TFLOP/s Nothing: it is memory-bound by design

Monitoring commands:

nvidia-smi --query-gpu=name,clocks.sm,clocks.max.sm,power.draw,power.limit,temperature.gpu,utilization.gpu --format=csv -l 1
nvidia-smi -q -d PERFORMANCE          # current throttle reasons
dcgmi dmon -e 1002,1003,1004,1005     # SM active, SM occupancy, tensor pipe active, DRAM active
ncu --set full -o report python my_kernel.py   # Nsight Compute: per-kernel speed-of-light analysis
nsys profile -o timeline python train.py      # Nsight Systems: whole-program timeline
Pitfall

utilization.gpu in nvidia-smi only reports the fraction of time some kernel was running. A GPU running a single tiny kernel continuously shows 100% while using 2% of its capability. Use DCGM's SM_ACTIVE (1002), SM_OCCUPANCY (1003), PIPE_TENSOR_ACTIVE (1004) and DRAM_ACTIVE (1005), or compute MFU, to know what's really happening.

Timing GPU code correctly

GPU calls in PyTorch are asynchronous: the Python line returns before the GPU finishes. Timing with time.time() around a call measures only the launch. Always synchronise, warm up, and repeat:

import torch
a = torch.randn(8192, 8192, device="cuda", dtype=torch.bfloat16)
b = torch.randn_like(a)
for _ in range(3):                    # warm-up: cuBLAS picks kernels, clocks ramp up
    a @ b
start, end = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(20):
    a @ b
end.record()
torch.cuda.synchronize()
ms = start.elapsed_time(end) / 20
print(f"{2 * 8192**3 / (ms / 1e3) / 1e12:.0f} TFLOP/s")

For benchmarking kernels, triton.testing.do_bench handles warm-up, cache flushing and statistics for you.

12. Common misconceptions

Belief Reality
"More FLOP/s means faster inference." Decode speed tracks memory bandwidth. H200 beats H100 for decode with identical FLOP/s.
"100% GPU utilisation means the GPU is fully used." It means a kernel was running. Check SM and tensor activity.
"Bigger matrices are always more efficient." Mostly, but wave and tile quantization create sawtooth dips at specific sizes.
"Higher occupancy is always better." Compute-bound kernels often prefer low occupancy with big register tiles.
"FP8 doubles speed." Only for the compute-bound matmuls. Memory-bound parts speed up by the byte reduction, and some ops stay in BF16.
"Sparse TFLOP/s is what I'll get." Dense is what almost everyone gets.

Exercises

Using the peak-FLOP/s formula, estimate an H100's dense FP8 throughput. What single factor changes compared with BF16?

Show answer

FLOPs per tensor core per clock double (2,048 instead of 1,024 for FP8). 132 × 4 × 2,048 × 1.83 × 10⁹ ≈ 1,979 TFLOP/s. SM count and clock are unchanged.

An A100 has 2.0 TB/s of bandwidth and ~600 ns memory latency. How many bytes must be in flight to saturate it, and how many per SM (108 SMs)?

Show answer

2.0 × 10¹² × 600 × 10⁻⁹ = 1.2 MB total; ≈ 11 KB per SM.

A kernel uses 128 threads per block, 128 registers per thread and no shared memory. What is its occupancy on an H100, and what limits it?

Show answer

Registers per block = 128 × 128 = 16,384 → 4 blocks fit (65,536 / 16,384). 4 blocks × 4 warps = 16 warps → 16/64 = 25%, limited by registers.

What is the arithmetic intensity of a BF16 matmul of shape (64 × 8192) @ (8192 × 8192)? Is it compute- or memory-bound on an H100? On a B200?

Show answer

FLOPs = 2 × 64 × 8192 × 8192 ≈ 8.59 × 10⁹. Bytes = 2 × (64 × 8192 + 8192² + 64 × 8192) ≈ 136 MB. AI ≈ 63. Memory-bound on both (ridge ≈ 295 on H100, ≈ 281 on B200). Attainable ≈ 3.35 TB/s × 63 ≈ 211 TFLOP/s on H100; ≈ 504 TFLOP/s on B200.

With 128×128 tiles on a 132-SM GPU, which is more efficient: M = N = 2,048 or M = N = 2,176? By how much?

Show answer

2,048: 256 tiles, 2 waves, 97% wave efficiency. 2,176: 17 × 17 = 289 tiles, 3 waves, 289/396 = 73%. The 2,176 case does 13% more work but needs 50% more waves.

Estimate batch-1 decode speed for an 8B model in BF16 on an H100 and on an H200, assuming 85% of peak bandwidth and ignoring the KV cache.

Show answer

16 GB per step. H100: 16 / (3.35 × 0.85) ≈ 5.6 ms → ~178 tokens/s. H200: 16 / (4.8 × 0.85) ≈ 3.9 ms → ~255 tokens/s. Same compute, 43% faster, entirely from bandwidth.

A team reports 100% GPU utilisation in nvidia-smi but training throughput is poor. List three measurements you would take next.

Show answer

(1) MFU from tokens/s and model size. (2) DCGM SM_ACTIVE and PIPE_TENSOR_ACTIVE to see whether tensor cores are busy. (3) An Nsight Systems or PyTorch profiler timeline to find idle gaps, data-loader stalls, many small kernels, or un-overlapped communication. Also check clocks and throttle reasons.

Why does moving from BF16 to FP8 weights help decode more at batch 1 than at batch 256?

Show answer

At batch 1, decode is purely weight-bandwidth-bound, so halving weight bytes nearly halves step time. At batch 256, the matmuls are near the ridge point and KV-cache reads (not reduced by weight quantization) are a larger share of traffic, so the relative gain is smaller. FP8 still helps by freeing memory for a larger batch.

Project: A GPU buyer's guide for your workload

Business problem: a startup serving an open 8B–70B model is choosing between H100, H200 and B200 capacity for next year. Sales decks quote peak FLOP/s. The CFO wants cost per million tokens for their traffic.

  1. Model it on paper. Use memory_planner.py to estimate capacity, speed and $/M tokens for each GPU at your realistic context length and concurrency. Record your predictions.
  2. Measure. Rent one of each GPU type for an hour (~$15 total). Run microbench.py on each and save microbench.csv. Then serve the same model with vLLM and run a load test at 1, 16 and 64 concurrent users (Chapter 19 has a script).
  3. Compare. Put predicted vs measured tokens/s side by side. Explain every gap larger than 25% (for example: KV-cache reads, attention kernel efficiency, scheduler overhead).
  4. Recommend. Write a one-page memo: "For our traffic mix, GPU X at $Y/hour gives $Z per million tokens at p95 latency under N ms. Here is the break-even against GPU W."

This project shows exactly the reasoning infrastructure teams use in real purchasing decisions, and it gives you calibrated intuition for every later chapter.
